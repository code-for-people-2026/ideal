# 平台 MVP 草案：咨询转介闭环

> 草案 v0.1 · 2026-07-05
>
> 目的：把“人人有 Agent 的底层网络”先压成一个能验证的平台闭环。本文只整理当前共识，不改动 `cfp-mono/街坊味` 的实现。

## 0. 一句话定位

我们要做的不是一个中心化点评平台，也不是一个普通专家咨询平台，而是一个以人为责任主体、以 Agent 为接口、以承诺记录为骨架的基层网络平台。

第一版 MVP 不做全量本地生活，不做完整联邦，也不做支付系统。它只验证一个最小闭环：

> 一个人通过自己的 Agent 发起咨询需求，经由不超过 4 跳的人脉探测找到可咨询对象；双方在责任实名后形成咨询承诺；咨询完成后产生双向评价、可选感谢、可选知识沉淀；这些记录在授权边界内成为下一次查询的证据。

## 1. 核心判断

### 1.1 平台从第一天存在

平台不是未来才长出来的“副产物”，而是一开始就存在的协议层、查询层、授权层、证据层。不同之处在于：

- 平台不应直接占有用户的原始记忆、偏好、评价和关系。
- 平台只保存最小必要事实、授权索引、承诺记录和可审计使用记录。
- 排序、推荐、解释可以由可替换的排序器和用户自己的 Agent 完成。

### 1.2 第一版闭环选“咨询”

咨询比私房菜、维修、看娃更轻：

- 没有配送、食品安全、资质、支付等重负担。
- Agent 可以强参与：澄清需求、路由转介、生成摘要、标注回答可信状态。
- 它仍然能验证平台最重要的东西：人脉探测、责任身份、承诺记录、双向评价、授权沉淀。

### 1.3 不是找专家，而是找有经验的人

第一版不要做成“专家入驻咨询平台”。更准确的场景是：

- 我想问一个做过社区私房菜的人，起步时怎么处理接单、防漏、定价和邻里信任。
- 我想问一个有经验的妈妈，怎么找靠谱托管。
- 我想问一个邻居，附近哪个儿科医生不坑。
- 我想问一个用过 AI 的照护者，怎么记录老人吃药。

## 2. 核心对象

### 2.1 Actor：认证责任主体

`Actor` 是平台里的责任主体，可以是：

- 个人
- 公司
- 登记组织
- 平台自身

第一版不直接认证家庭、临时小组、家委会、互助队等非正式组织。这些生活中的主体可以作为某个已认证 Actor 的对外身份存在。

### 2.2 Profile / Persona：对外身份

`Profile` 或 `Persona` 是责任主体在某个场景下的对外身份。

例子：

- 桃子这个个人 Actor，可以有“桃子的厨房”这个服务身份。
- 一个公司 Actor，可以有“某某维修队”这个服务身份。
- 码成工平台这个 Actor，可以有“Agent 托管服务”“查询 API 服务”等服务身份。

铁律：

> 每个可形成承诺的服务身份，必须有且只有一个当前责任主体。

### 2.3 CapabilityEndpoint：能力端点

搜索和探测阶段，不必直接暴露完整的人。平台可以先暴露“能力端点”：

- 能回答什么问题
- 以什么方式回答
- 是否接受陌生或半熟人咨询
- 需要什么介绍强度
- 是否匿名展示
- 背后有平台认证责任主体兜底，但可在承诺草案阶段再揭示

能力端点解决的是：“有没有一个可能能回答这个问题的人或服务身份愿意接触？”

### 2.4 Commitment：承诺记录

底层对象不是狭义订单，而是 `Commitment`。

咨询、订单、互助、借东西、陪诊、看娃、家教，都可以是 Commitment 的特化。

咨询型 Commitment 至少包含：

| 字段 | 含义 |
|---|---|
| requester | 发起咨询的人 |
| provider | 被咨询者或其服务身份 |
| topic | 咨询主题 |
| scope | 问什么，不问什么 |
| format | 文字、语音、通话、线下 |
| timeBox | 15 分钟、30 分钟、一次异步问答等 |
| consideration | 免费、感谢、互助、人情、付费、捐赠等 |
| confidentiality | 内容是否记录、是否可总结、是否可分享 |
| status | proposed / accepted / completed / canceled / disputed |

### 2.5 Probe / Relay：人脉探测与转介

第一版支持深度不超过 4 的人脉探测。关系路径默认用于路由，不默认向发起人展示。

路径例子：

```text
A -> B -> C -> D
```

默认规则：

- 中间人是否透露身份，由中间人自己决定。
- 发起人可以要求中间人必须透露身份；这会过滤掉不愿透露的中间人。
- 中间人默认看不到最终承诺双方的实名和承诺详情。
- 中间人只能看到发起人授权给自己的内容，以及允许自己转发给下一跳的内容。
- 中间人可以基于自己的认知重述转发内容，但不能篡改原始意图锚点。

## 3. 咨询闭环

### 3.1 四阶段

#### Probe：探测

匿名或半匿名。只传概括需求，不形成承诺。

#### Match：匹配意向

双方知道存在一个可能对象，但仍可以隐藏真实身份。可以交流范围、形式、是否愿意继续。

#### Trust Check：二次可信度探测

匹配到能力端点后，发起人不应只依赖平台的身份验证。发起人可以再次利用自己的社交网络，对候选对象或其服务身份做可信度探测。

这一步解决的是：

> “平台确认了这个人是谁，但我是否应该相信他/她适合回答这个问题？”

二次探测可以询问：

- 有没有人认识这个候选对象？
- 有没有人接受过类似咨询？
- 这个人在该主题上是否有真实经验？
- 有没有与该人相关的承诺记录、评价或争议？
- 是否存在只在熟人网络里才知道的风险提示？

这一步仍然不形成正式承诺。发起人可以根据二次探测结果决定：

- 继续进入 Commitment Draft
- 要求更多身份或经验说明
- 换另一个候选对象
- 放弃本次咨询

#### Commitment Draft：承诺草案

进入具体时间、具体问题、对价、保密、记录授权前，双方责任身份必须互相可见。

### 3.2 对接后的实名

“真的对接”从进入 Commitment Draft 开始。此时服务提供者和消费者都必须责任实名。

这里的实名分三层：

| 层级 | 说明 |
|---|---|
| Platform Real Identity | 平台掌握法定实名或认证材料，用于兜底、争议、反欺诈 |
| Counterparty Real Identity | 正式对接后，对方能看到足以确认“我在和谁形成承诺”的实名信息 |
| Public Display Identity | 搜索和探测阶段使用的展示名、服务身份、匿名能力端点 |

正式对接后，应互相展示真实姓名或认证名、服务身份、责任说明。无需默认暴露身份证号、手机号、住址。联系可以继续走站内通道。

### 3.3 身份验证和需求对接分离

需求对接解决：“谁可能能回答？”

身份验证解决：“我是否信任这个人？”

被咨询者最终的身份、可信度，可以由发起人再次在自己的社交网络中问询。也就是说，找到能力端点只是第一步；用平台身份验证确认“此人是谁”是第二步；用自己的人脉网络判断“我是否信任此人”是第三步；决定是否形成承诺是第四步。

平台身份验证和人脉可信度探测不能互相替代：

- 平台验证负责确认责任主体存在、可追责。
- 人脉探测负责确认该主体在具体场景里的可信度、经验和口碑。
- 发起人的 Agent 应把两类证据分开展示，不能把“平台已认证”包装成“值得信任”。

## 4. 转介内容与隐私

### 4.1 双内容机制

发起人对每一跳可以准备两份内容：

1. 给当前中间人的内容。
2. 允许当前中间人转给下一跳的内容。

中间人可以基于第二份内容再次简化或重述。

### 4.2 原始意图锚点

为了防止需求在 4 跳之后变形，每次转发都必须保留一个不可篡改的原始意图锚点。

例子：

```text
原始意图锚点：
A 想找有经验的人咨询“全职妈妈做社区私房菜起步，如何处理接单、防漏、定价和邻里信任”。
```

中间人可以补充：

- 我为什么觉得你适合。
- 我认识 A，靠谱。
- 我建议你只回答定价部分。
- 我理解这个问题是某种经营起步咨询。

但不能悄悄把原始需求改成招商、合作、推销或其他含义。

### 4.3 中间人反馈与感谢

中间人可以获得最小反馈：

- 已被接收
- 未被接收
- 路由已结束
- 感谢你的转介

中间人默认不能看到：

- 双方是谁
- 最后聊了什么
- 是否成交或付费
- 谁评价谁
- 具体咨询结果

感谢默认是表达，不是资产：

- 不可交易
- 不可提现
- 不进入排行榜
- 默认私密
- 公开展示需感谢发出者和接收者都同意

## 5. AI 回答与 Review 状态

### 5.1 Agent 代答不是正式咨询

被咨询者的 Agent 可以先回答基础问题，以减少本人重复沟通。

但 Agent 代答和真人咨询必须分层：

| 类型 | 含义 |
|---|---|
| Agent-mediated interaction | Agent 基于授权材料回答，本人未亲自承诺 |
| ConsultationCommitment | 本人接受咨询，有时间、范围、边界和双向评价 |

Agent 代答不能自动生成“D 完成了一次咨询”的记录。

### 5.2 回答可信状态

每条 Agent 回答应有明确状态：

| 状态 | 含义 |
|---|---|
| unreviewed_ai | 纯 AI 回答，未由本人确认 |
| reviewed_answer | 本人看过这一次回答，并确认可代表自己 |
| certified_knowledge | 本人预先确认过一段知识、FAQ 或经验，Agent 基于它回答 |

咨询者可以要求只看真人 review 过的回答。可信状态必须进入筛选和排序条件，而不是只做 UI 标签。

### 5.3 只支持本人 Review

第一版只支持本人 review，回归人本身。

组织或平台官方回答也必须落到具体人：

```text
张三（码成工维护者）已确认。
李四（某公司运营负责人）已确认。
```

不能出现“某组织已确认”但没有具体人的无名确认。

### 5.4 Review 带版本

Review 是带版本的承诺，不能静默漂移。

```text
AnswerVersion
- v1 reviewed
- v2 corrected
- v1 deprecatedAt
- deprecatedReason
```

已被别人看到或基于其形成承诺的回答，不能无痕删除；可以撤回未来使用、标记过期、发布修正版。

## 6. 评价、证据和排序

### 6.1 平台只记录，不做最终评判

平台不生成全局个人总分，不替所有人判断某条差评是否应影响另一个场景。

平台保存：

- 承诺事实
- 评价原文
- 标签
- 上下文
- 可见范围
- 争议状态
- 授权记录

查询者自己的 Agent 根据其价值观、风险偏好、关系网络和场景需求解释这些证据。

### 6.2 双向评价

咨询完成后，评价必须双向。

被咨询者也可以评价咨询者：

- 问题是否清楚
- 是否尊重边界
- 是否按约支付或回馈
- 是否泄露内容

双方都可以控制评价可见范围。

### 6.3 咨询内容默认不进入证据层

区分三类数据：

| 类型 | 默认规则 |
|---|---|
| Commitment Metadata | 可进入双方记录，默认双方可见 |
| Consultation Content | 默认私密，不进入平台证据层 |
| Extracted Experience | 双方同意后，可作为去身份化经验沉淀 |

咨询结束后，双方 Agent 可以询问是否愿意提炼一条可分享经验。默认不分享。

### 6.4 排序器可分叉

底层平台保存授权证据，不输出唯一“最佳”。

排序层可以可替换、可分叉：

- 熟人优先版
- 价格优先版
- 妈妈圈口碑版
- 食品安全洁癖版
- 左翼互助版
- 商家友好版

排序器只能在用户授权下查询证据，不应永久复制原始评价。排序规则和版本应公开。

### 6.5 默认排序

默认排序不应给单一“第一推荐”。应返回：

- 候选集
- 推荐理由
- 风险提示
- 关系路径解释的可见部分

产品表达应是：

> 这些人或服务与你的关系路径和需求最接近。

而不是：

> 这是最佳答案。

## 7. 偏好画像

### 7.1 偏好是价值表达

产品上不展示“权重滑杆”，而是让用户用人话表达价值观和风险偏好。

例子：

- 熟人用过更重要。
- 食品类服务优先安全和稳定，不贪便宜。
- 找人看娃只接受熟人或熟人实际接触过的人。
- 支持邻里小生产者。
- 出现爽约争议时提醒我，不自动排除。

技术上再落成排序参数。

### 7.2 全局底座 + 场景覆盖

偏好画像应有全局底座和场景画像。

```text
GlobalPreferenceProfile
- 基础价值观
- 基础风险偏好

ScenarioPreferenceProfile
- food
- childcare
- repair
- medical
- education
- secondhand
- mutual_aid
```

场景偏好继承全局偏好，但可以覆盖。

### 7.3 偏好数据归属

偏好原文只存在用户自己的 Agent 里。经过授权，可以：

- 分享给平台训练和理解
- 生成去身份化模板供他人复制
- 分享给特定人

必须区分：

| 授权类型 | 含义 |
|---|---|
| Private | 只在我的 Agent 里服务我 |
| Shareable Template | 去身份化后分享给别人复制 |
| Training Donation | 明确同意给平台用于改进推荐理解 |

偏好模板只是参考策略，不能作为背书。复制前，自己的 Agent 必须解释这套模板意味着什么，并获得确认。

## 8. 数据分层

### 8.1 四类存储

| 层级 | 数据 | 默认位置 |
|---|---|---|
| 私人记忆 | 偏好原文、敏感需求、未公开评价草稿、家庭情况、关系备注 | 用户 Agent 私域 |
| 双方承诺记录 | 谁和谁达成了承诺、服务身份、时间、状态、对价、履约结果 | 平台最小必要事实 |
| 授权评价/经验 | 评价原文、摘要、标签、可见范围 | 原文归用户，平台保存授权索引 |
| 公共/社区索引 | 可被当前查询者看到的证据、关系路径、履约统计 | 平台查询层 |

### 8.2 共同承诺记录不能单方物理删除

Commitment 是双方共同事实，不能被单方无痕删除。

可以：

- 对自己隐藏
- 撤回对第三方可见
- 标记争议
- 请求更正
- 到期归档
- 法律或安全原因申请删除或脱敏

单方私密记忆才是单方可删。

## 9. 平台自身也是 Actor

平台不能站在网络之外。平台至少有三种身份：

| 身份 | 含义 |
|---|---|
| Infrastructure Actor | 提供协议、存储、查询、排序器市场、授权系统 |
| Service Provider Actor | 给用户、生产者、排序器开发者提供软件服务 |
| Governance Actor | 处理投诉、争议、违规、数据删除、排序器下架等治理动作 |
| Mediator Actor | 作为需求、关系、证据、承诺的中介，负责授权路由和协议执行 |

平台不是取消中介，而是把中介从数据所有者、排序裁判、流量地主，降级为协议执行者、授权路由者、证据保管者和可审计服务提供者。

平台作为 Mediator Actor，也必须被同一套机制约束：中介行为应产生可审计记录，也应允许用户评价。例如：平台是否正确传达需求，是否过度暴露身份，是否把“平台认证”误导性包装成“值得信任”，是否尊重转介路径授权，是否真实执行导出、删除和撤回。

平台使用用户数据训练模型，也是一种 Commitment。用途、范围、期限、撤回方式、收益或回馈方式都应明确。

平台服务可以拆成具体 offerings：

- Agent hosting
- Evidence storage
- Query API
- Sorter marketplace
- Mini-app runtime
- Identity / responsibility mapping
- Data export / deletion

第一版平台服务失败时，不承诺强赔偿。承诺：

- 透明记录
- 数据导出
- 人工修复
- 当期费用减免或退款
- 不承诺间接损失赔偿

## 10. Forkability

### 10.1 可 fork 的四层

| 层级 | 含义 |
|---|---|
| Code fork | 代码可复制，别人可自己部署 |
| Protocol fork | 协议可兼容或修改 |
| Governance fork | 审核、排序器上架、争议处理规则可分叉 |
| Data portability | 用户可导出自己的数据，迁移到另一个网络 |

网络可 fork 不等于数据库可复制。只有数据主体授权的数据可以迁移。

### 10.2 第一版最小承诺

MVP 阶段至少做到：

1. 核心 schema 文档公开。
2. 核心 API 文档公开。
3. 用户数据可导出，至少 JSON/CSV。
4. 排序器可替换。
5. 服务条款写明不主张用户原始数据所有权。
6. 内部跑一次迁移演练。

铁律：

> 每新增一种业务数据，都必须同时定义：谁拥有、谁可见、能否导出、导出给谁看得懂。

## 11. MVP 验收

第一版平台的目标不是功能完整，而是跑通一次真实咨询闭环：

```text
Need -> Candidate -> Probe/Relay -> Trust Check -> Commitment Draft -> Consultation -> Review -> Thanks -> Reuse
```

最低验收标准：

1. 一个真实用户通过 Agent 表达咨询需求。
2. Agent 将需求结构化，并生成可转发版本。
3. 平台在不超过 4 跳内进行人脉探测。
4. 中间人按授权转发，默认不可见最终承诺双方情况。
5. 至少一个能力端点接受匹配意向。
6. 发起人可对候选对象发起二次可信度探测，平台身份验证和人脉可信度证据分开展示。
7. 进入 Commitment Draft 前，双方责任实名。
8. 咨询完成后，形成双向评价。
9. 中间人收到默认私密的感谢。
10. 咨询内容默认不公开，但可选择沉淀去身份化经验。
11. 下一次相似查询可以在授权边界内复用这条经验或评价证据。

## 12. 暂不做

第一版不做：

- 完整本地生活平台
- 支付系统
- 人情币或积分资产
- 转介排行榜
- 全局个人信用分
- 全网联邦
- 完整导入迁移
- 陌生专家咨询市场
- 让中间人默认看到承诺结果
- 咨询内容默认进入平台知识库

## 13. 待继续 grill 的问题

1. 第一版真实试点人群是谁：码成工内部朋友、辩论赛同路人、妈妈群、还是街坊味相关人群？
2. 深度 4 探测的 UI 是站内消息、微信转发，还是 Agent 生成转发卡片？
3. 平台第一版如何完成个人认证：微信实名、人工审核、邀请制、还是熟人背书？
4. “咨询主题”如何分类，才能既能搜索又不把人压扁成标签？
5. Commitment Draft 的最小字段有哪些，哪些必须用户确认？
6. 纯 AI 回答、基于认证材料回答、本人 review 回答，第一版如何在界面上清楚区分？
7. 第一版是否允许付费咨询，还是完全禁止支付只留字段？
8. 排序器第一版是否只内置一个默认排序器，还是同时做一个可替换接口？
9. 数据导出第一版做到什么粒度才算不是空头支票？
10. 平台自身的数据使用记录，第一版是否就做用户可见页面？





## 14. 双许可：商业模式与牛马互助模式

平台不必拆成两个互不相干的网络。更准确的结构是：同一套底层平台能力，适用两种许可 / 协议模式。

这个结构类似“开源免费、商用收费”的双许可：

```text
Common Core
- Actor / Profile / CapabilityEndpoint
- Commitment / Evidence / Authorization
- Ranking / Export / Governance

商业模式（Commercial License）
- 面向企业、中产、高客单价、非工友场景
- 市场价收费
- 可购买托管、私有部署、排序器、咨询工具、技术支持
- 不自动享受牛马互助网络权益
- 收入按反哺契约支持牛马互助模式

牛马互助模式（Mutual-Aid License）
- 面向工友、互助场景、公益/合作社场景
- 工友价、互助义务、数据权利、可导出、可 fork
- 使用者若想享受互助模式福利，也必须向工友让利
- 承载平台的宗旨方向
```

“无协议网络”这个说法不准确。商业模式也受平台服务条款、数据条款、反滥用条款、可审计条款约束；只是它不享受、也不承担牛马互助协议下的权益和义务。

### 14.1 双许可边界

商业许可可以买软件服务，但不能购买互助网络的信任资产。

商业模式可以买：

- Agent 托管
- 私有部署
- 企业内部咨询网络
- 排序器工具
- 数据导出工具
- 工作流自动化
- 技术支持

商业模式不能买：

- 工友关系图
- 互助模式评价
- 低价服务资格
- 互助网络优先转介
- 用户原始偏好和私密经验
- 牛马互助模式中的声誉背书

铁律：

> 双许可共享技术，不共享特权；商业许可反哺牛马互助模式，但不能购买互助网络的信任资产。

### 14.2 反哺契约

如果允许商业模式存在，必须把反哺写成结构性约束，否则商业模式会自然吸走用户、收入和团队注意力。

反哺契约至少包括：

1. **技术反哺**：商业模式做出的底层能力，默认同步给牛马互助模式，不得只给旧版或阉割版。
2. **收入反哺**：商业模式净收入固定比例进入牛马互助模式预算，不得只靠“有余力再说”。
3. **人力反哺**：每个周期固定比例团队时间投向牛马互助模式。
4. **数据隔离**：两种许可下的身份、授权、评价、偏好分离，不得默认互相训练或污染。
5. **品牌区隔**：商业模式不能打着牛马互助旗号获取信任。
6. **互助模式优先权**：两边底层能力冲突时，牛马互助模式的核心承诺优先维护。

商业模式赚的钱不是创始人可分配利润，而是平台 Actor 的受约束收入，仍受收入差距、不分红、不套现、资产归社会等自我约束。

### 14.3 生产者与消费者不是固定身份

商业模式可能更吸引生产者，牛马互助模式可能更吸引消费者。但平台不应简单“站生产者”或“站消费者”。

同一个人可以在不同 Commitment 中扮演不同角色：

- 桃子卖饭时是生产者，找人陪诊时是消费者。
- 码农做咨询时是生产者，找育儿帮助时是消费者。
- 小商家可能被平台压迫，也可能压迫顾客或员工。

平台要站的是具体关系中的弱势一方，而不是抽象身份。每个 Commitment 都应标注：

- `licenseMode`: commercial / mutual_aid
- `applicableProtocol`: commercial-terms / cattle-license / other
- 价格、让利、风险和责任边界

牛马互助模式福利不能被无让利者自动享受。想享受工友价，就必须在相应场景遵守牛马互助协议。

### 14.4 牛马互助协议的传染逻辑

这套双许可应继承 GPL 式传染逻辑：

> 如果你想按牛马互助协议价使用我们的软件服务，你也必须把你的软件或服务按牛马互助协议价提供给工友。  
> 如果你不愿遵守，可以购买商业许可，但不能享受牛马互助模式权益。

因此，双许可不是“现实和理想各玩各的”，而是同一平台内的两种进入方式：商业模式负责现金流和技术压力测试，牛马互助模式负责宗旨、工友价、进出口平衡和互助治理。
## 15. 互助网络中的进出口平衡

进出口平衡不应是粗暴的金额顺差/逆差，而是互助网络中的资格与治理指标。

互助网络平衡的是：

> 从网络获得的互助，与向网络提供的互助之间的关系。

至少包含四个维度：

| 维度 | 含义 |
|---|---|
| Value 价值 | 从网络获得的服务、优惠、帮助 |
| Labor 劳动 | 向网络提供的时间、技能、照护、经验、转介 |
| Concession 让利 | 是否以工友价或互助价向符合对象提供服务 |
| Risk / Burden 风险与负担 | 是否承担不舒服、不确定、脏活累活、情绪劳动、兜底责任 |

第一版不做单一顺逆差分数，而做互助账本。

```text
MutualAidLedger
- received: 获得过什么帮助、优惠、咨询、服务
- contributed: 提供过什么帮助、让利、转介、经验、review
- context: 服务对象是谁，是否工友，是否高风险/高负担
- visibility: 只自己看 / 对方可见 / 网络治理可见
```

原则：

> 互助网络不追求每个人收支相抵，而追求强者不净抽取、弱者可被托住、贡献不只按市场价格计算。

### 15.1 允许长期逆差

互助网络必须允许一些人长期逆差，例如老人、病人、单亲妈妈、失业者、残障者、照护压力爆表的人、遭遇临时灾难的人。

个人层面允许弱者长期被托住；网络整体防止强者长期净抽取。

### 15.2 互助资格状态

进出口平衡更适合作为资格系统，而不是惩罚系统。

```text
MutualAidStanding
- open: 正常
- encouraged_to_contribute: 建议贡献
- contribution_required_for_discount: 继续享受工友价需提供贡献或说明
- exempt: 被社区/平台确认可长期接受帮助
- suspended_for_extraction: 明显套利或违规
```

评价、感谢、转介可以算贡献，但权重应低。高权重贡献应来自实际服务、让利、照护、陪伴、辅导、维修、高质量经验沉淀、帮助弱者完成真实需求、组织和治理劳动。

## 16. 反刷与反套利

互助网络里的刷单，刷的不是销量，而是互助资格。因此不能只靠单一反作弊算法，要靠关系成本、承诺成本、证据成本、治理成本共同防刷。

常见刷法：

1. 刷贡献：互相假咨询、假转介、假感谢。
2. 刷信任：小圈子互相好评。
3. 刷让利：伪造工友价服务。
4. 刷人脉路径：制造假关系，绕过深度探测。
5. 刷弱者身份：假装工友或困难状态，长期低价消费。
6. 平台自刷：平台为了证明互助网络有效而灌水。

### 16.1 反刷原则

1. **单一行为不高权重**：感谢、评价、转介不能直接换取高互助资格。
2. **高权重贡献绑定完整 Commitment**：需求、匹配、承诺、履约、双向评价链条越完整，证据越强。
3. **看关系多样性，不只看数量**：不同关系来源、不同社区、不同时间、不同场景更可信。
4. **贡献有观察期**：新贡献先 pending，过一段时间无争议后再计入 standing。
5. **让刷单有真实成本**：实名责任、时间盒、结果确认、可抽查、可争议。
6. **异常只触发审计，不自动定罪**：平台可以降权、要求说明、进入人工/社区审计，但不能黑箱判人作恶。
7. **无公开贡献排行榜**：互助贡献不可交易、不可提现、不作为单一信用分。
8. **平台自身不得注水**：平台操作也进入审计日志。

```text
Anti-Gaming v0
- 感谢、评价、转介默认低权重
- 高权重贡献必须绑定完整 Commitment
- 同一小圈子高频互评自动降权
- 新贡献有观察期
- 异常只触发降权/审计，不自动定罪
- 无公开贡献排行榜
- 平台自身操作进入审计日志
```

第一原则不是抓刷单，而是不要把互助资格设计成能靠低成本行为快速套利的东西。

## 17. 治理：平台大法官与小法官

平台作为 Governance Actor，不应垄断事实判断。可以学习“外卖小法官”的陪审机制，但不能变成群众审判、站队投票或熟人围攻。

治理结构：

```text
平台大法官
- 程序、隐私保护、证据打包、执行、申诉、紧急风控

小法官 / 陪审员
- 从合格用户中抽取
- 基于最小必要证据判断普通纠纷

专门处理通道
- 涉及骚扰、家暴、儿童老人安全、医疗法律财务、身份欺诈、线下人身风险等
- 不交给普通小法官
```

原则：

1. 小法官看证据，不看八卦。
2. 小法官随机或按资格抽取，不是全网围观。
3. 必须有回避机制，与双方有强关系、利益关系、历史冲突的人应回避或被标记。
4. 小法官只给建议或初裁，平台负责程序兜底和执行。
5. 治理结果只处理平台内权益，不审判人格。
6. 普通纠纷默认不公开；严重风险事件只在必要范围内提示，且保留申诉和版本。

```text
Dispute
- commitmentId
- claim
- requestedRemedy
- evidenceBundle
- visibility
- status

Juror
- actorId
- qualification
- conflictCheck
- decision
- reasoning

PlatformRuling
- finalAction
- reason
- appealWindow
- auditLog
```

小法官适合处理：是否按约完成、是否迟到/爽约、评价是否明显不相关、感谢/转介是否误用、互助资格是否涉嫌刷贡献。

小法官不适合处理：家暴、骚扰、隐私泄露、医疗法律财务专业判断、身份欺诈、儿童老人残障者安全、线下人身风险。

铁律：

> 平台是程序大法官，不是事实垄断者；小法官是有限陪审员，不是群众审判团。小法官只能判断具体 Commitment 或具体评价是否成立，不能审判一个人的人格。
