# 第一部分：第一版到底做什么（收敛后的共识）

## 0. 一句话定位

我们要做的，不是一个中心化点评平台，也不是一个专家咨询平台，而是一个**以人为责任主体、以 Agent 为接口、以承诺记录为骨架**的基层信任网络**底座**。

宗旨方向：

> **让人 agent 化 → 连入互联网 → 让生产者和消费者基于信任形成社区。**

第一版不验证这整张网。它只赌一件最脆弱、一旦不成立整个构想就垮的事：

> **一条署名的、经具体人背书的信任，能不能被记录下来、并被第二个人第二次用上。**

## 1. 核心判断（收敛后）

### 1.1 平台从第一天就是“底座”，但只记录、不路由

平台不是未来才长出来的副产物，而是一开始就存在的协议层、记录层、授权层、证据层。但第一版严守一条边界：

> **平台只记录信任，不制造信任、不路由需求。**

架构分层：

| 层 | 是什么 | 第一版做不做 |
|---|---|---|
| 底座 | 协议 / 记录 / 证据层：Agent + Commitment + 双向评价 + 感谢 | **做** |
| 街坊味 | 建在底座之上的第一个上层 app（点单）：**下单动作本身就生成 Commitment** | 复用现有，接上底座 |
| 撮合大中介 | 更上层、自动路由/撮合、可替换/可 fork 的应用 | **不做**（后续可长出来） |

### 1.2 信任不是平台制造的，是导入和沉淀的

平台不生产信任，只搬运和沉淀信任：在一个**现实中已有信任**的圈子里起步，把每一次生产者↔消费者的承诺和互评记录下来，让它**可携带、可被下一次查询看到**。这样绕开“陌生人之间从零制造信任”的死结，也守住“数据平权”。

### 1.3 第一场景选“桃子的厨房”，不选一次性咨询

第一版主闭环用一个**有真实复购、信任真的要紧、天然有熟人介绍、且我们够得着的**服务场景——社区私房菜「桃子的厨房」+ 桃子的熟客圈。

为什么不是一次性咨询：咨询问完就散，**复用价值极低**，人们最没动力去记录，测不出我们真正想测的“信任能否被复用”。咨询在第一版**降为附属轻动作**（下单前先问两句），不是主闭环。

第一版**平台只记录，不碰支付、不碰配送**——做饭、给钱、取餐全在线下。重的是**场景真实度**，不是平台实现负担。

### 1.4 人脉转介链是涌现的，不是我们主动做的

原 v0.1 把信任重量全压在“4 跳链式人脉探测”上。现在明确：

- **4 跳链式接力探测 = 网络自己会长出来的涌现功能，第一版不主动做、不写机制，只观察它会不会自己发生。**
- 第一版真正支撑的信任传递，收敛成一个干净的原语：**至多 1 个中介**（见 2.1）。

## 2. 第一版做什么（最小系统）

### 2.1 三种信任来源，一套机制

第一版支撑的信任传递深度上限为 1，有三种来源：

| 来源 | 结构 | A 凭什么信 C |
|---|---|---|
| 0 跳·直接 | A 本来就认识 C | 自己的直接经验 |
| 1 跳·熟人 | A—B—C，B 同时认识 A 和 C | A 信任熟人 B 的选择 |
| 1 跳·社区 | A 和 B 不一定熟，但同属高信任容器（如业主群），B 在群里署名推荐 C | A 信“这个我信任的群里的人 + B 敢署名” |

关键收口：**三种来源不需要三套系统**。它们都是同一件事——

> **一个具体的人 B 署名推荐了 C，而 A 是通过一个自己已经信任的通道（私聊，或自己所在的群）遇到这条署名背书的。**

差别只在分享通道（私发 vs 群发），不是两套机制。

### 2.2 Agent 形态：代我表达、代我背书，不代我承诺

第一版的“人 agent 化”严格卡在：

- **做**：Agent 代表你**表达需求 / 下单**，代表你在朋友问起时给一句**署名背书**，并持有你的承诺记录和大白话偏好（数据在你侧 / 你授权的存储）。
- **不做**：Agent **不替你做出别人据此建立信任的承诺**（不做“分身决策”）。信任与承诺始终锚定在真人身上。

双入口，按关系距离渐进——越熟越轻，越远越需要 Agent 出面解释和背书：

| 入口 | 给谁用 | 形态 |
|---|---|---|
| 接龙式卡片 | 桃子现有熟客**直接下单** | 微信群里的接龙小程序卡片，极轻 |
| 独立 Agent 小程序 | **二阶新人**（经熟客介绍来、和桃子还陌生） | 聊天式界面，Agent 出面展示背书、答疑、引导下单 |

角色分层（不是每个人都一样重）：**生产者重**（桃子要有服务身份「桃子的厨房」）、**消费者中**（能下单 + 存记录 + 事后被朋友问时背书）、**介绍人最轻**（只需点一下“我确实介绍了”+ 收感谢）。

### 2.3 核心对象：Commitment（最小字段）

底层对象是 `Commitment`（承诺记录），第一版在**下单那一刻（交易前）生成**——在街坊味里，下单动作本身就是这条承诺的自然副产物。

| 字段 | 含义 | 备注 |
|---|---|---|
| requester | 发起方（消费者，如小李） | 责任主体 |
| provider | 提供方 / 服务身份（如「桃子的厨房」） | 责任主体 |
| introducer | 介绍人 / 背书人（如小李、或业主群邻居） | 可空，需本人同意 |
| introducerContext | 背书发生的通道（私聊 / XX 业主群） | 可空，轻量上下文，见 2.4 |
| subject | 一次订餐 / 一次服务 | |
| status | proposed / completed / canceled | 第一版够用 |
| review | 双向评价（消费者→提供方、提供方→消费者） | 见 2.5 |
| thanks | 给介绍人的感谢 | 默认私密，不可交易、不进排行榜 |

**砍掉**（第一版不做）：scope、format、timeBox、consideration（对价金额）、confidentiality、争议对象、licenseMode 等——留给后续协议层。

### 2.4 署名背书卡片：介绍 + 捕获 + 展示，三合一

介绍人如何被牢牢绑上一条 Commitment，这是整条信任链的命门。第一版机制：

1. 熟客 B 在自己 Agent 里点“推荐桃子的厨房”→ 生成一张**带 B 署名背书的小程序卡片**（“我经常吃，靠谱”）。
2. B **私发**给某个二阶新人 A，或**群发**进业主群。
3. A 一点进入：`introducer = B` **自动绑定**，`introducerContext` 记下通道（私聊 / 该群），A 开屏第一眼就看到 B 的署名背书。

一个动作同时完成**介绍、介绍人捕获、背书展示**，是微信最自然的分享/接龙机制，桃子和阿姨都会用。且因为卡片是 B 亲手生成分享的，介绍人天然真实、责任在群里公开可追溯，防了乱选介绍人。

### 2.5 数据归属

守“数据平权”宗旨 + “平台不做全局总分”：

- 评价**原文归个人**，存在本人 Agent 侧 / 本人授权的存储。
- 底座只存**最小事实索引**（谁 ↔ 谁 成交过、经谁介绍、状态）。
- 评价**默认只对本人授权的人/关系可见**，永不进全局公开评分。
- **复用只做“本人 Agent 署名背书”**：朋友问“谁做饭靠谱”→ **本人**的 Agent 凭自己的记录、在本人授权下答“桃子，我经阿姨介绍试过，靠谱”。**第一版不建跨用户检索/查询层**（那是上层 app 的活）。

### 2.6 实名

第一版**实名 = 微信身份 + 自报真名**即可，不做 KYC / 人工审核那套重认证。私房菜熟客圈本就半实名，重认证留给以后。

## 3. 一次成功闭环（happy path）

1. 桃子有一个 Agent + 服务身份「桃子的厨房」。
2. 新客小李想找靠谱家常菜；邻居阿姨（**既认识小李、也认识桃子**）把桃子推荐给小李——**在线下 / 微信发生，平台不管**。（若是业主群里陌生邻居的署名推荐，则走 2.1 的“社区”来源，机制相同。）
3. 阿姨在 Agent 里生成署名背书卡片发给小李；小李一点进入 → 经他的 Agent 下单“向『桃子的厨房』买一次饭”→ **生成 Commitment**（requester=小李、provider=桃子的厨房、introducer=阿姨）。桃子确认接单；阿姨确认“我确实介绍了”。
4. 做饭、给钱、取餐——**全在线下，平台不碰支付和配送**。
5. 完成后双向评价：小李评桃子（好吃 / 干净 / 靠谱），桃子评小李（好沟通 / 按约取付），阿姨收到一句**默认私密**的感谢。
6. **验收点**：此后有第二个二阶新人（如小李的朋友、或群里另一位邻居）因为看到这条署名背书而下单——**可携带信任第一次被复用**，第一版就算跑通。

## 4. 验收标准（可证伪）

第一版是一次实验，不是“做个东西出来”。

- **唯一硬验收点（生死线）**：至少发生 **1 次“署名背书 → 二阶新人因此下单”**的完整复用。发生 0 次 = 第一版没跑通，别自欺。
- **量的地板**：≥ 5~10 条**带 introducer 的真实 Commitment** + 双向评价基本完成。
- **定性生死线**：熟客到底**愿不愿意主动分享署名背书卡片**。如果几乎没人愿意署名拉人，“署名可携带信任”这个内核就是死的——**早死早好**，比堆功能强。

## 5. 第一版明确不做

不做支付、不做配送、不做 4 跳链式探测、不做跨用户检索 / 查询层、不做撮合大中介、不做排序器市场、不做双许可机制、不做互助账本 / 资格、不做反刷系统、不做陪审团治理、不做 KYC、不做全局信用分。

> 这些全是**底座之上、以后再长**的东西（详见第二部分）。第一版底座砍到骨头：**Agent（双入口）+ Commitment（带介绍人）+ 双向评价 + 感谢 + 署名背书卡片**。

## 6. 待继续 grill 的问题（已更新）

v0.1 里的多数问题已在本轮敲定（场景、信任机制、平台角色、Agent 形态、入口、介绍人捕获、实名、复用、数据归属、验收）。剩余待钉：

1. 街坊味现有实现里，“下单 → 生成 Commitment”具体怎么接？需要改哪几处？（落地排期时再定，本文不改代码）
2. 署名背书卡片的最小 UI：一张卡片上放哪些信息才既能建立信任又不过度暴露桃子？
3. “感谢”默认私密，但介绍人贡献如何在不做排行榜的前提下让本人有正反馈？
4. 二阶新人首单后的**留存 / 复购**，是否要作为第二个观察指标（硬验收只看首单，但留存决定网络能不能滚起来）？
5. 第一版试点具体从哪个真实圈子切入：桃子现有熟客群、某个业主群、还是辩论赛 / 妈妈群同路人？

# 第二部分：后续可能长出来的协议层（第一版不做）

> 以下是 v0.1 已经想过、但明确**推迟**的更完整设计。第一版底座不实现；它们大多是“建在底座之上、可替换 / 可 fork 的上层应用或治理规则”。保留于此供以后参考，**不作为当前承诺**。

## 7. 更完整的对象与探测模型

- **Actor / Profile / CapabilityEndpoint**：责任主体、对外服务身份、可先暴露的“能力端点”（能回答什么、以什么方式、是否接受陌生咨询、需要多强介绍、是否匿名）。铁律：每个可形成承诺的服务身份，必须有且只有一个当前责任主体。
- **Probe / Relay（4 跳链式探测）**：深度 ≤ 4 的人脉探测、双内容机制（给中间人的内容 + 允许转给下一跳的内容）、不可篡改的**原始意图锚点**、中间人身份揭示规则、中间人最小反馈。→ **第一版不做**，视为涌现功能。
- **三层实名**：Platform Real Identity（兜底 / 争议 / 反欺诈）、Counterparty Real Identity（正式对接后互见）、Public Display Identity（探测阶段的展示名 / 匿名端点）。→ 第一版只做“微信身份 + 自报真名”。
- **身份验证与需求对接分离**：找到能力端点 → 平台验证“此人是谁” → 自己人脉判断“我是否信任” → 决定是否形成承诺。平台验证 ≠ 值得信任，两类证据必须分开展示。

## 8. AI 代答与 Review 状态

- Agent 代答 ≠ 正式咨询：`Agent-mediated interaction`（本人未亲自承诺）与 `ConsultationCommitment`（本人接受、有边界和双向评价）必须分层。
- 回答可信状态：`unreviewed_ai` / `reviewed_answer` / `certified_knowledge`，且必须进入筛选和排序条件，不只是 UI 标签。
- 只支持本人 review，组织回答也要落到具体人（“张三（码成工维护者）已确认”），不能“某组织已确认”。
- Review 带版本，不能静默漂移（v1 reviewed / v2 corrected / deprecatedReason）。

## 9. 评价、证据与排序器市场

- 平台只记录，不做全局个人总分。保存承诺事实、评价原文、标签、上下文、可见范围、争议状态、授权记录。
- 双向评价：完成后双方互评，各自控制可见范围。
- 咨询 / 服务内容默认不进证据层；`Commitment Metadata` / `Consultation Content` / `Extracted Experience` 三类分层，经验沉淀需双方同意。
- **排序器可分叉**：熟人优先、价格优先、妈妈圈口碑、食品安全洁癖、左翼互助、商家友好……排序器只能在授权下查询证据，规则和版本公开。默认排序不给单一“最佳”，返回候选集 + 推荐理由 + 风险提示 + 可见的关系路径。

## 10. 偏好画像

- 偏好是价值表达（用人话，不用权重滑杆），技术上再落成排序参数。
- 全局底座 `GlobalPreferenceProfile` + 场景覆盖 `ScenarioPreferenceProfile`（food / childcare / repair / medical / education / secondhand / mutual_aid）。
- 偏好原文只在本人 Agent 里；授权分 `Private` / `Shareable Template` / `Training Donation`。模板只是参考策略，不作背书。

## 11. 数据分层与 Forkability

- 四类存储：私人记忆（用户 Agent 私域）、双方承诺记录（平台最小必要事实）、授权评价 / 经验（原文归用户、平台存授权索引）、公共 / 社区索引（平台查询层）。
- 共同承诺记录不能单方物理删除，只能对自己隐藏 / 撤回第三方可见 / 标记争议 / 请求更正 / 到期归档 / 依法脱敏。单方私密记忆才单方可删。
- 可 fork 四层：Code fork / Protocol fork / Governance fork / Data portability。网络可 fork ≠ 数据库可复制，只有数据主体授权的数据可迁移。
- 铁律：每新增一种业务数据，都必须同时定义：谁拥有、谁可见、能否导出、导出给谁看得懂。

## 12. 平台自身也是 Actor

平台至少有四种身份：Infrastructure Actor、Service Provider Actor、Governance Actor、Mediator Actor。平台不取消中介，而是把中介从数据所有者、排序裁判、流量地主，降级为协议执行者、授权路由者、证据保管者、可审计服务提供者。平台的中介行为也应产生可审计记录、也应允许用户评价。平台用用户数据训练模型，也是一种 Commitment（用途 / 范围 / 期限 / 撤回 / 回馈须明确）。

## 13. 双许可：商业模式与牛马互助模式

同一套底座能力，两种许可模式：

- **商业许可**：面向企业 / 中产 / 高客单价场景，市场价收费，可买托管 / 私有部署 / 排序器 / 工具 / 支持；不自动享受互助网络权益；收入按反哺契约支持互助模式。
- **牛马互助许可**：面向工友 / 互助 / 公益场景，工友价、互助义务、数据权利、可导出、可 fork；想享受福利就必须向工友让利（GPL 式传染）。

铁律：**双许可共享技术，不共享特权；商业许可反哺互助模式，但不能购买互助网络的信任资产**（工友关系图、互助评价、低价资格、优先转介、原始偏好、声誉背书都不能买）。反哺契约含技术 / 收入 / 人力反哺、数据隔离、品牌区隔、互助模式优先权。生产者与消费者不是固定身份，平台站的是具体关系中的弱势一方。每个 Commitment 标注 `licenseMode` / `applicableProtocol` / 价格让利风险边界。

## 14. 互助网络的进出口平衡

不做粗暴的金额顺逆差，而做**互助账本**（received / contributed / context / visibility），衡量四维：Value / Labor / Concession / Risk-Burden。原则：不追求人人收支相抵，而追求强者不净抽取、弱者可被托住。允许老人 / 病人 / 单亲妈妈 / 失业者等**长期逆差**。作为**资格系统**而非惩罚系统：`open` / `encouraged_to_contribute` / `contribution_required_for_discount` / `exempt` / `suspended_for_extraction`。评价 / 感谢 / 转介算贡献但权重低，高权重来自真实服务 / 让利 / 照护 / 治理劳动。

## 15. 反刷与反套利

互助网络里刷的是互助资格。靠关系成本 + 承诺成本 + 证据成本 + 治理成本共同防刷。原则：单一行为不高权重；高权重贡献绑定完整 Commitment；看关系多样性而非数量；贡献有观察期；让刷单有真实成本；异常只触发审计不自动定罪；无公开贡献排行榜；平台自身操作也进审计日志。第一原则不是抓刷单，而是**别把互助资格设计成能靠低成本行为快速套利的东西**。

## 16. 治理：大法官与小法官

平台作 Governance Actor，不垄断事实判断，可学“外卖小法官”陪审机制但不搞群众审判。结构：**平台大法官**（程序 / 隐私 / 证据打包 / 执行 / 申诉 / 紧急风控）+ **小法官 / 陪审员**（从合格用户抽取、看证据判普通纠纷、有回避机制）+ **专门通道**（骚扰 / 家暴 / 儿童老人安全 / 医疗法律财务 / 身份欺诈 / 线下人身风险，不交普通小法官）。铁律：平台是程序大法官不是事实垄断者；小法官是有限陪审员不是群众审判团，只能判断具体 Commitment 或评价是否成立，不能审判人格。
