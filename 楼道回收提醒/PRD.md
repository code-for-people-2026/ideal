# 楼道收一收 · MVP PRD

> 状态：概念验证稿
> 更新：2026-08-05
> 一句话：住户扫一下本层二维码直接上报，师傅在待办里看到要去的楼层，处理完点一下完成。

## 1. 问题

楼道里的纸箱、饮料瓶等可回收物是不定时出现的。师傅不知道哪层有东西，只能逐层查看或靠口头通知。这会浪费体力和时间，也容易漏收。

## 2. 目标

- 住户从看到二维码到上报成功，不需填写内容，理想情况下不再点第二下。
- 师傅打开小程序后，3 秒内看懂“现在去哪几层”。
- 处理完某层后，只用一次大按钮就能完成待办，且点错可撤销。

### 不做什么

MVP 不管理废品种类、重量、价格、住户姓名、门牌号、付款、积分、聊天或多小区调度。它只解决一个问题：**哪个楼层有需要回收或打扫的事项。**

## 3. 使用者与场景

| 角色 | 想完成的事 | 使用环境 |
|---|---|---|
| 住户 | 发现楼层需要回收或打扫时，顺手告诉师傅 | 手里可能拿着物品，在楼道里匆忙扫码 |
| 师傅 | 看清待处理楼层，处理完后勾掉待办 | 年纪较大，单手拿手机，可能在户外强光下使用 |

## 4. 核心流程

### 住户：扫码即上报

1. 住户把纸箱或饮料瓶放在约定位置。
2. 扫本层对应事项的二维码。入口已经携带“楼栋 + 楼层 + 事项类型”，住户不再选择。
3. 页面立即显示“正在上报”，随后显示“上报成功”以及本次记录的位置和事项。
4. 每次扫码都产生一次上报；同楼层、同类型已有未完成待办时，师傅端仍聚合为一条待办并更新上报次数和最近时间。
5. 住户不查看处理进度；照片和留言只在现场不好找时自愿补充。
6. 如果扫错或还没放好，30 秒内可点“撤回这次上报”。

### 师傅：看待办、处理、完成

1. 新楼层从“无事”变为“待处理”时，小程序尝试发一次通知。
2. 师傅打开首页，只看到未完成待办，按从高到低排列，方便从顶层一路向下处理。
3. 每条待办显示楼层、事项类型、多久前上报和累计上报次数。
4. 处理完后，直接点待办上的大按钮“收好了”或“打扫好了”。该待办立即从列表消失。
5. 页面暂时显示“刚才完成 8 楼，点错了？撤销”。撤销后待办恢复。
6. 完成后的新扫码形成一条新的待办，不与之前已完成的事项混合。

## 5. “处理完怎么勾掉”的决策

### 推荐：列表内一键完成 + 可撤销

这是 MVP 的默认方案。

- **比“到楼层后再扫码”少操作**：师傅已经在看手机，不必再对准墙上的码。
- **比“点进详情再确认”少一层页面**：每个楼层卡片直接有大按钮。
- **比滑动、长按等手势更容易学**：仅需单击，按钮不依赖隐藏手势。
- **用“操作后撤销”代替“操作前弹窗确认”**：绝大多数正常操作不被多问一次，点错仍可补救。

备选方案“师傅处理完后扫同一个楼层码自动完成”可在实地测试时比较，但不作为首发主流程。

## 6. 状态模型

系统记的是师傅尚未完成的“楼层待办事项”，不是住户需要跟踪的处理进度。

```text
无事
  │ 住户扫码上报
  ▼
待处理 ── 同楼层同类型再次扫码 ──▶ 仍是一条待办（次数 +1，更新时间）
  │ 师傅点“收好了 / 打扫好了”
  ▼
已完成 ── 后续再次扫码 ──▶ 新的待办
```

规则：

- 同一楼层、同一事项类型在未完成期间只保留一条待办，不生成多张卡。
- 每次扫码都是一次上报，并更新待办的最近上报时间和次数。
- 住户端只确认上报成功，不展示待办进度。
- 师傅完成待办后，后续新上报创建新的待办，不沿用已完成事项的次数和时间。
- 待办不自动过期。过夜仍显示“昨天”，避免没处理却被系统悄悄清掉。

## 7. 功能范围

### P0（必须有）

- 每层一个唯一二维码，可识别楼栋和楼层。
- 住户每次扫码都直接上报，并看到简洁的成功结果。
- 同楼层同类型的未完成上报聚合为一条师傅待办，并累计次数。
- 住户在短时间内可撤回本次上报。
- 师傅首页显示全部未完成待办及相对时间。
- 师傅一键完成，完成后可撤销。
- 无未完成待办时显示明确空状态：“现在没有要处理的”。

### P1（实地验证后再定）

- 微信订阅消息或其他到达通知，具体形态以小程序平台能力和师傅授权意愿为准。
- 一键切换“只看下一层”的引导模式。
- 打印二维码和楼层告示的管理页。

## 8. 易用性要求

- 核心正文不小于 18px，楼层数字尽可能使用 32px 以上。
- 主按钮高度不小于 52px，文字说完整的动作，不只放图标。
- 不使用左滑、双击、长按等隐藏手势作为必须操作。
- 不用红绿颜色单独表达状态，同时显示“待处理 / 无事”文字。
- 所有时间默认用“20 分钟前”“今天 8:20”“昨天”等口语化表达。
- 非必要不要求住户登录、授权头像昵称或填写手机号。

## 9. 成功指标（试用 2 周）

- 90% 以上的住户从扫码到看到成功页少于 5 秒。
- 师傅在无口头指导的情况下，能独立完成“看待办楼层 → 处理 → 完成”。
- 完成误操作率低于 5%，且测试用户知道如何撤销。
- 已上报但未被处理的遗漏率明显低于当前靠巡楼的方式。

## 10. 验收场景

1. 8 楼第一次被扫码，住户看到“上报成功”，师傅端出现一张“8 楼”待办。
2. 待办完成前再次扫码，住户仍直接看到“上报成功”；师傅端仍只有一张 8 楼待办，上报次数变为 2。
3. 师傅点“8 楼收好了”，8 楼立即移出未完成列表。
4. 师傅点“撤销”，8 楼回到原有排序位置，原等待时间和上报次数不丢失。
5. 8 楼完成后再次被扫码，师傅端生成一条新的 8 楼待办，次数从 1 开始。
6. 当全部待办完成后，首页明确显示“现在没有要处理的”。

## 11. 待实地确认

- 师傅实际习惯是从高层向下收，还是按通知先后收？
- 放置点能否统一到楼梯间？如果不能，是否真的需要精确到门牌号？
- 微信通知的授权和到达率是否足够可靠？首页待办列表必须在没有通知时仍可独立使用。
- 师傅更喜欢“一屏看全部”还是“一次只看下一层”？可用原型中的 A / C 方案对比。

## 12. 原型

打开当前发布原型 [index.html](./index.html)。这是不接真实数据的可丢弃原型，用来体验住户扫码直接上报、可选现场补充、同楼层未完成上报聚合，以及师傅在电梯楼层面板中完成待办和点错撤销。

在仓库根目录运行：

```bash
python3 -m http.server 4173
```

然后访问：

```text
http://127.0.0.1:4173/楼道回收提醒/
```
