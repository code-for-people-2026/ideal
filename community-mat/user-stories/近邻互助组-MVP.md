## 0. 怎么使用这份文档

这份文档描述“系统必须成立的行为”，实施对照原型描述“用户如何感知这些行为”。两者需要一起看，但互不替代：

- User Story 决定角色价值、业务规则和验收结果。
- 工程原型展示主路径中的界面、状态迁移与信息边界。
- 原型里的示例文案、布局、颜色和动画不是接口契约。
- 没有写进 Story 或产品决议的原型细节，不自动成为开发需求。
- 异常处理、安全、性能、可访问性和可观测性需要在技术设计中另行补齐。

## 1. 角色

| 角色 | 说明 | 最终责任 |
|---|---|---|
| 求助者 / 顾客 | 提出需求、查看亲历、选择服务者 | 决定是否联系、是否授权数据 |
| 消费者 / 亲历先行者 | 分享本人真实消费经历 | 核对并确认自己发布的表述 |
| 服务者本人 | 实际提供服务 | 接单、报价、时间、变更与最终承诺 |
| 服务者 Agent | 依据服务者已确认的信息接待 | 不得越权替真人作最终承诺 |
| 近邻系统 Agent | 整理需求、解释权限、展示亲历来源 | 不代表服务者，不作质量担保 |
| 平台组织者 | 维护系统与社区支持 | 规则、合规、安全与运营 |

## 2. Epic A：完成一次服务后沉淀亲历

### US-A01 · 消费者收到待确认的服务记录

> 作为刚完成服务的消费者，我希望从服务者发来的微信卡片进入待确认记录，以便核对本次服务是否真实准确。

**验收条件**

- Given 鲁师傅创建了一条待确认服务记录
  When 赵阿姨在微信私聊中收到并点击卡片
  Then 小程序打开对应记录，不要求她从首页自行寻找。
- 卡片和落地页明确显示服务者、服务内容、日期、金额与当前“待消费者确认”状态。
- 未确认记录不得计为双方确认履约事实。

**原型定位**：场景 A / `?variant=private`

### US-A02 · 消费者确认记录并决定是否公开为亲历

> 作为消费者，我希望先核对服务事实，再决定公开为亲历卡或仅自己保存，以便保留对本人经历的控制权。

**验收条件**

- Given 赵阿姨打开待确认记录
  When 她确认记录无误
  Then 系统先完成事实确认，再单独询问公开范围。
- “确认事实”与“公开亲历”是两个独立动作；确认不等于公开。
- 选择“仅自己保存”后，记录仍归本人可见，不进入其他消费者可发现的亲历网络。
- 发现内容有误时，可以退出并回到原沟通渠道，不得强迫确认。

**原型定位**：场景 A / `?variant=confirm`

### US-A03 · 消费者从消息首页继续处理任务

> 作为存量消费者，我希望像使用微信一样从消息列表进入各个对话和功能，以便理解每个服务需求是独立上下文。

**验收条件**

- 首页以会话与待处理事项为中心，不使用无关的信息流抢占注意力。
- 每条会话显示参与方、最近状态和待处理动作。
- 从二级会话返回时回到消息首页，并保留该会话状态。

**原型定位**：场景 A / `?variant=home`

### US-A04 · 消费者复用并分享自己的亲历卡

> 作为消费者，我希望在卡夹里找到并转发自己的亲历，以便在真实求助出现时帮助邻居。

**验收条件**

- 只展示本人拥有且有权分享的亲历。
- 每张卡显示服务者、本人使用次数、最近一次时间和证据状态。
- 转发动作生成带本人署名与授权范围的小程序卡片。
- 转发不会把其他私人记忆或联系人一并公开。

**原型定位**：场景 A / `?variant=mycards`

### US-A05 · 消费者从可见亲历网络寻找服务者

> 作为有新需求的消费者，我希望用自然语言描述需求并查看来自可见亲历网络的候选，以便基于真实经历作判断。

**验收条件**

- 系统只检索当前用户有权查看的亲历。
- 候选展示亲历人数、卡片数量、新鲜度、地理范围和可用信息。
- 候选顺序不得表达全局质量排名或平台担保。
- 选中候选后进入该服务者的独立会话。

**原型定位**：场景 A / `?variant=discover`

### US-A06 · 消费者表达成为服务者的意向

> 作为也有技能的消费者，我希望向平台说明自己能提供什么，以便开始服务者接入流程。

**验收条件**

- 用户可以先用自然语言描述技能与大致服务方式。
- 提交结果是“服务意向”，不是自动获得平台认证或立即公开接单。
- 系统明确告知后续由工作人员联系确认。

**原型定位**：场景 A / `?variant=provide`

## 3. Epic B：用本人亲历回应微信群里的真实求助

### US-B01 · 求助保留在原有关系场

> 作为求助者，我希望继续在熟悉的微信群提出需求，以便无需先学习或加入一个新平台。

**验收条件**

- 求助发生时，近邻互助组尚未介入。
- 群聊中不自动抓取、复制或公开求助内容。
- 只有有意回应的亲历先行者主动把截图带入小程序后，系统才开始处理。

**原型定位**：场景 B / `?variant=wechat`

### US-B02 · 亲历先行者用截图匹配已有亲历

> 作为亲历先行者，我希望导入群聊截图并匹配自己的已有亲历，以便用最少操作回应真实求助。

**验收条件**

- 系统从截图生成可核对的需求摘要。
- 匹配范围默认只包含当前用户自己的亲历卡。
- 候选卡解释与需求匹配的具体依据。
- 亲历先行者必须主动选择并分享，系统不得自动发回微信群。

**原型定位**：场景 B / `?variant=pioneer`

### US-B03 · 没有匹配时补录并确认本人陈述

> 作为有相关经历但没有现成卡片的亲历先行者，我希望用语音补录并核对整理结果，以便快速分享准确的本人陈述。

**验收条件**

- 语音转写和结构化结果在分享前完整展示给本人核对。
- 用户可以重新录入或取消。
- 新补录明确标记为“本人陈述、尚无双方确认”。
- 系统不得把补录内容伪装成平台已验证的履约事实。

**原型定位**：场景 B / `?variant=pioneer`，点击“没有合适的，补录一张”

### US-B04 · 亲历卡回到原微信群

> 作为求助者，我希望在原微信群中看见邻居的自然语言回应和亲历卡，以便理解这是谁分享的、为什么与我有关。

**验收条件**

- 分享卡带亲历先行者身份、服务者名称、关键匹配点和证据等级。
- 点击前，求助者仍处在微信群环境。
- 点击后才打开近邻互助组，不假装平台拥有微信群上下文。

**原型定位**：场景 B / `?variant=shared`

## 4. Epic C：第一次进入时建立信任

### US-C01 · 首次访问者先理解数据与付费承诺

> 作为第一次打开近邻互助组的求助者，我希望在查看亲历前理解平台如何使用数据和如何收费，以便决定是否继续。

**验收条件**

- 首次进入显著说明“不出售消费记录和关系链”。
- 说明亲历、评价和联系方式默认不公开，并支持授权、导出和删除。
- 说明首月免费、月卡阶梯和“当前 App 运行 / 跨 App 研发与毛利”的资金用途。
- 不使用诱导放弃隐私权的暗黑模式文案；拒绝或退出必须真实可用。

**原型定位**：场景 B / `?variant=requester` / 首次欢迎与月卡分支

### US-C02 · 求助者查看足够但不过量的亲历证据

> 作为求助者，我希望看见与当前需求相关的有限亲历证据，以便判断是否继续联系服务者。

**验收条件**

- 展示推荐关系、本人原话、使用次数、最近时间、证据状态和需求匹配点。
- 明确推荐人没有佣金收益。
- 明确这是有限本人亲历，不是平台质量担保。
- 不展示完成当前判断不需要的私人记忆或关系链。

**原型定位**：场景 B / `?variant=requester` / 亲历详情

### US-C03 · 跨小程序查看服务前获得授权

> 作为求助者，我希望在跳到服务者专属小程序前知道目标和将传递的数据，以便控制自己的需求信息。

**验收条件**

- 跳转前显示目标小程序和需要传递的最小需求摘要。
- 未经明确确认不得传递额外聊天记录、关系链或其他需求。
- 取消跳转后留在当前亲历详情。

**原型定位**：场景 B / `?variant=requester` / “看看本周有什么”

## 5. Epic D：人 + Agent 的混合会话

### US-D01 · 顾客看清房间参与者和数据范围

> 作为顾客，我希望进入房间时看清真人、服务者 Agent 和系统 Agent 的身份与权限，以便知道每句话由谁负责。

**验收条件**

- 房间顶部持续展示顾客、服务者本人、服务者 Agent 和近邻系统 Agent。
- 每条消息标明发送主体与主体类型，Agent 不得使用真人身份样式。
- 进入时展示来源和带入的需求摘要。
- 服务者及其 Agent 看不到顾客的其他会话。

**原型定位**：场景 B / `?variant=requester` / “先问桃子两句”

### US-D02 · 顾客选择与 Agent 或真人沟通

> 作为顾客，我希望选择消息发给服务者 Agent 还是真人，以便兼顾效率和责任确认。

**验收条件**

- 输入区明确显示当前接收者，并允许切换。
- 服务者 Agent 只能回答服务者已经确认的菜单、时间和流程信息。
- 接单、报价、临时调整和最终承诺必须由服务者本人确认。
- 真人加入后仍在同一房间中，历史责任主体不被改写。

**原型定位**：场景 B / `?variant=requester` / 桃子的厨房房间

### US-D03 · 新需求创建独立会话

> 作为顾客，我希望提出其他需求时得到一个干净的新会话，以便旧服务者无法看到无关信息。

**验收条件**

- 新需求不默认继承旧服务者房间的聊天内容。
- 系统只使用用户主动输入的新需求和有权查看的亲历网络。
- 用户可返回旧会话，两边状态互不覆盖。

**原型定位**：场景 B / `?variant=requester` / “我还有其他需求”

### US-D04 · 为新服务者建立新的混合会话

> 作为顾客，我希望从候选亲历中选择新服务者并建立同样透明的混合会话，以便复用一致的信任与责任规则。

**验收条件**

- 候选卡解释亲历来源、人数、新鲜度、距离和可用时间。
- 选择候选后新建独立房间，不复用桃子房间的参与者或数据范围。
- 新房间继续区分新服务者本人、其 Agent 和近邻系统 Agent。

**原型定位**：场景 B / `?variant=requester` / 新需求匹配与周师傅房间

## 6. 跨 Story 的硬边界

以下规则优先级高于任何单页视觉：

1. **人负责**：Agent 可以表达、整理和代答，但不能替真人作最终承诺。
2. **证据分级**：本人陈述与双方确认履约事实永远不能混为一类。
3. **最小可见**：每个分享、跳转和会话只获得完成当前任务所需的数据。
4. **按房间隔离**：新需求、新服务者、新会话默认不继承旧房间内容。
5. **不作担保**：亲历匹配不是全局排名，也不是平台质量担保。
6. **无推荐佣金**：亲历先行者不因推荐次数获得佣金、排名或推广权。
7. **显式授权**：公开、分享、跨小程序传递和真人加入均需要可理解的用户动作。

## 7. 原型覆盖与非覆盖

| 范围 | 当前工程原型 | 开发前仍需补充 |
|---|---|---|
| Happy path | 覆盖 | — |
| 角色、身份与消息归属 | 覆盖 | 账号与鉴权设计 |
| 页面级状态迁移 | 覆盖 | 服务端状态机、幂等与并发 |
| 数据可见范围 | 展示原则 | 字段级权限矩阵、审计日志 |
| 微信分享与小程序跳转 | 模拟 | 微信开放能力约束与失败回退 |
| OCR / 语音 / Agent | 模拟结果 | 模型选择、置信度、人工修订与成本 |
| 异常、空状态、撤销 | 少量覆盖 | 完整异常矩阵 |
| 隐私导出与删除 | 仅说明承诺 | 真实数据生命周期与合规流程 |
| 月卡与支付 | 展示说明 | 支付、退款、账务与价格变更 |
| 非功能需求 | 不覆盖 | 性能、安全、可访问性、监控与告警 |

## 8. 建议的工程拆分顺序

1. 先实现身份主体、证据等级、授权范围和会话隔离四个领域约束。
2. 用 US-B01 → B04 + US-C02 跑通“微信群求助 → 亲历卡 → 查看证据”的最小只读闭环。
3. 加入 US-D01 → D02，跑通混合会话与真人承诺边界。
4. 加入 US-A01 → A04，让亲历能够从真实履约中持续产生并复用。
5. 最后实现 US-A05、A06、D03、D04，扩展新服务发现与供给接入。
6. US-C01 的隐私与付费承诺在首次公开测试前必须落到真实能力，不能只保留展示文案。
