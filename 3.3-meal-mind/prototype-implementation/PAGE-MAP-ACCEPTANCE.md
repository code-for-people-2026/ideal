# 页面地图重做验收标准

## 目标

页面地图是给产品与开发团队查看的“手机端客户旅程图”。手机页面本身是静态故事帧，用来说明家庭菜单规划者为什么使用排好菜、如何跨页面完成任务、最终得到什么结果；只有旅程筛选、手机聚焦、拖动和缩放属于画布查看操作。核心旅程没有覆盖到的页面与状态，才放进补充功能验证区。

页面地图不是需求文档、领域模型、Issue 看板，也不能把“排菜单 / 菜品库 / 历史 / 我的”四个一级入口直接当成四条用户故事。

## 信息来源与优先级

- 客户原型决定人物、使用动机、叙事顺序和价值表达。主旅程既要覆盖“生成菜单 → 对照查看 → 单道替换 → 确认保存 → 查看结果”，也要说明新用户如何先建立可用的家庭餐型与菜品池。
- 可运行工程原型决定当前页面、可点击行为、状态变化和已实现边界。
- 页面地图只保留中文用户语言；数据归属、失败边界和未来接口等技术内容暂不进入公开原型，后续需要时再形成独立工程设计文档。
- 三者冲突时，不编造已实现能力：保留客户旅程，缺失节点明确标成“计划中”。

## 一票否决项

- 继续按“排菜单 / 菜品库 / 历史 / 我的”拆成四条互不相干的功能线。
- 只有页面或组件状态，没有人物动机、任务起点、跨页面动作和可验证结果。
- 把搜索、筛选、候选卡片等局部交互包装成独立的核心用户故事。
- 核心旅程在“保存成功”“复制成功”之前结束，或没有展示结果去向。
- 为了避免页面重复而打断真实旅程，要求开发人员自行猜测跨入口跳转。
- 箭头出现 `Dish`、`WeekPlan draft`、`HouseholdRule` 等英文领域名，而没有直接使用中文说明用户刚做了什么、接下来会看到什么。
- 把手机故事帧做成可以现场切换、输入或提交的运行原型，导致页面地图状态与后续节点不一致。
- 把只用于查看的菜单格、摘要标签做成按钮或选中态，让人误以为可以直接修改。
- 任何流程节点使用横向文档卡、表格、审计面板或长段文字代替手机页面。
- 用与运行原型不一致的数量、状态或能力伪装成“已实现”。
- 只画静态图片，旅程筛选、单页面聚焦、缩放、适配和核心交互不可用。

## 画布结构

画布分为两个清晰层级，核心旅程必须比补充验证更靠前、更醒目。

### A. 核心客户旅程

按真实生活任务组织端到端流程，可以跨越多个一级入口。每条旅程必须注明：

1. 谁在什么情况下开始。
2. 她想解决什么问题。
3. 依次点击和看到什么。
4. 哪一步完成任务。
5. 完成后结果保存在哪里、下次如何继续使用。

### B. 补充功能验证

只收纳核心旅程没有覆盖到、但开发仍需实现或验证的内容，例如：

- 菜品库搜索、分类筛选和独立菜品详情。
- 菜品新增、编辑、停用等计划中能力。
- 空菜品库、无候选菜、目标周已有菜单、保存失败等边界状态。
- 周切换、候选卡片、规则选项等局部控件状态。

补充验证可以采用较短的页面状态链，但必须标成“补充验证”，不能与端到端旅程并列宣称用户价值。

## 四条核心客户旅程

### E2E-01：第一次使用，准备好排菜基础

**人物与场景：** 新用户第一次进入排好菜，需要先告诉系统家里怎么吃饭、每餐通常怎么搭配，以及有哪些真正会做、会吃的菜。

至少包含以下连续步骤：

1. 进入首次准备，理解家庭基础将用于之后每一次生成。
2. 确认家庭人数、工作日安排天数，以及午饭和晚饭等餐次。
3. 选择默认每餐结构；画面展示“2 荤 2 素 1 汤”“2 荤 1 素 1 汤”“1 荤 2 素 1 汤”三个常用预设，并保留“自定义搭配”。
4. 使用家常菜起步包减少首次录入成本。
5. 逐道确认家里常吃的菜，并看到当前菜品数量是否足以支撑所选餐型。
6. 看到家庭餐型和菜品池摘要，进入第一次排菜。

**完成结果：** 用户拥有一套可继续维护的默认餐型和已确认菜品池，可以生成第一周菜单。

### E2E-02：给家里排好本周菜单

**人物与场景：** 家庭菜单规划者在周末准备下一周午饭和晚饭，不想每天临时决定吃什么。

至少包含以下连续步骤：

1. 进入排菜单，看到本周或下周尚未安排，并可切换周次。
2. 点击生成，得到五天十餐的完整菜单。
3. 按日期对照午饭和晚饭；菜单格只读，不通过点击菜名假装修改。
4. 从明确的“换这道”入口进入替换，选择自动候选或去菜品库手选。
5. 返回本周菜单，明确看到只替换了这一道，其余餐次保持不变。
6. 查看十餐总览和软规则提醒，确认保存。
7. 看到保存成功，并可从历史进入完整只读菜单。

**完成结果：** 本周菜单成为可查看、可复用但不可直接篡改的历史记录。

### E2E-03：沿用上一周，少改几道菜

**人物与场景：** 新一周到来时，用户觉得上周大部分安排仍然合适，希望复用后再微调。

至少包含以下连续步骤：

1. 从历史列表找到上一周并打开完整菜单。
2. 点击复制到下一周，确认目标周次。
3. 系统创建新的可编辑菜单草稿，不修改原历史记录。
4. 返回排菜单查看复制结果，按需要替换几道菜。
5. 确认并保存下一周菜单。

**完成结果：** 原历史记录保持只读；下一周得到一份独立、可继续调整的新菜单。

### E2E-04：家庭情况变化后重新排菜

**人物与场景：** 家庭人数、忌口或餐次发生变化，用户希望下一次生成自动遵守新规则。

至少包含以下连续步骤：

1. 从“我的”查看当前家庭规则摘要。
2. 修改人数、工作日餐次、忌口或每餐结构。
3. 保存后看到新规则的明确摘要。
4. 回到排菜单生成新的周菜单。
5. 在生成结果中验证新规则已经应用。

**完成结果：** 新规则只影响之后生成的菜单，不回头修改已保存的历史菜单。

当前运行原型尚未完整实现的步骤必须统一标成“计划中”，但整条旅程仍要画完，便于团队理解目标闭环。

## 页面复用与跨入口规则

- 一级入口仍固定为“排菜单 / 菜品库 / 历史 / 我的”，只表示用户当前所在位置，不再充当旅程分类。
- 同一页面可以出现在不同客户旅程中，只要用户确实会在不同场景经过它；实现时复用同一个页面模板和数据定义，不复制业务逻辑。
- 同一旅程跨入口时必须把实际跳转画出来，不能只在行尾写数据交接后结束。
- 箭头主文案使用用户语言，例如“这道不合适，换一道”“复制后继续调整”“保存好，下周可复用”。
- 页面地图的步骤编号、箭头、状态和结果全部使用中文；领域对象名不在公开原型画布上混排。
- 已保存菜单始终只读；复制创建新草稿，不能覆盖已有目标周。
- 菜品库手选只决定替换候选，真正写入当前菜单仍在排菜单旅程中完成。

## 画布与手机页面标准

- 保留当前暖灰画布、白色画板、顶部工具栏、拖动、滚轮缩放、适配和单画板聚焦，不重新设计视觉体系。
- 每个流程节点保持 `390 × 844` 左右比例的独立手机画板；允许统一等比缩放，不允许压扁或拉宽。
- 复用现有 `public/assets/iphone/Bezel.png`、`public/assets/status/ios-status-icons.svg` 和客户原型的米白、砖红、深绿、浅金视觉令牌。
- 手机内至少包含状态栏、页面标题、真实内容区和主要按钮或状态；常规页面包含四项底部导航，首次准备流程在完成前可隐藏底部导航，避免提前离开。
- “全部”视图展示四条核心旅程和补充验证区；点击某条旅程后，该旅程在常见桌面视口下可读；点击单手机后以接近 1:1 的比例居中。
- 画布上的非手机文字只允许旅程名称、一句场景、步骤编号、箭头标签、完成结果和“已实现 / 计划中 / 补充验证”状态。

## 画布查看与静态展示验收

- 顶部筛选固定为“全部 / 首次准备 / 本周排菜 / 复用上周 / 规则变更 / 补充验证”，点击后正确更新 `aria-pressed` 并聚焦相应区域。
- 首次准备按静态节点依次展示家庭餐次、默认餐型、菜品池起步方式和菜品确认，并在完成页说明下一步是第一次排菜。
- 手机内的主要按钮、返回、一级导航、搜索框、筛选、选择和提交控件全部是静态画面，不改变任何节点状态；跨页面关系只由相邻故事帧和连接器表达。
- 核心旅程手机页中的人数、餐次、餐型和候选菜只展示该步骤的既定状态，不允许现场切换；需要表现另一状态时，应增加独立流程节点。
- 每餐结构提供三个常用预设和一个“自定义搭配”入口；页面地图只展示当前选中状态，完整设置行为放在运行原型中。
- 菜单总览中的菜名和“当前查看：荤菜”只负责阅读，不呈现按钮语义、手型光标或无效选中态；替换必须从“换这道”等明确动作进入。
- 候选菜卡只展示“已选 / 备选”结果，不承担临时单选交互；保存或返回动作负责推进到下一张手机状态。
- 复制旅程必须用后续节点展示下一周可编辑草稿；历史原记录仍保持只读。
- 规则保存后必须用独立节点展示摘要，并在后续生成节点说明规则已被使用。
- 点击每个手机画板可聚焦；拖动画布、滚轮缩放、“缩小 / 放大 / 适配”均可用。
- 一级导航保持“项目入口 / 运行原型 / 页面地图 / 客户原型”，每个名称只对应一个目的地；暂不公开实现说明。

## 内容与边界验收

- 每个核心节点都能回答“用户为什么来到这里、点击后发生什么、如何知道成功”。
- 客户旅程文案优先使用家庭排菜者能理解的表达，不把测试术语、开发任务或验收结论写进手机界面。
- 已实现节点必须与可运行工程原型的交互和数据一致。
- 计划中节点使用统一虚线或状态标识，不能伪装成已完成能力。
- 补充验证区必须覆盖核心旅程未覆盖的重要页面和边界，但不能重复讲述已经完整覆盖的主流程。
- 技术边界仍需保持：菜单生成与修改归属 `WeekPlan`，菜品来源归属 `DishCatalog`，历史保存归属 `SavedPlan`，家庭规则归属 `HouseholdRule`。

## 最终质量门槛

- 主 agent 先按本文件逐条走通四条客户旅程，再检查补充验证覆盖；不能只统计页面数量。
- 必须保存“全部”、四条核心旅程、“补充验证”和单手机聚焦截图，并检查每张截图的叙事顺序和可读性。
- 1280 × 720 和当前应用内浏览器视口均无工具栏遮挡、画布裁切或横向页面变形。
- 页面控制台无 warning/error；键盘焦点清晰；`prefers-reduced-motion` 可用。
- `npm test`、`npm run build:pages`、仓库级 `.github/scripts/build-pages-site.sh` 和 `git diff --check` 全部通过。
- 出现任一一票否决项，必须返工后再交付；未经本地评审，不提交、不推送、不合并。
