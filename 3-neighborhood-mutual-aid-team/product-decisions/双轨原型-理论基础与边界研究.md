# 牛马互助平台双轨原型：理论基础与边界研究

> 状态：原型拆分决策参考
> 日期：2026-07-31
> 研究范围：同一数字产品如何同时维护一份面向潜在客户的体验／价值原型，以及一份面向工程师、对照 User Story 实施的参考原型。
> 资料原则：只采用标准机构、方法提出者或官方实践指南的一手资料；本文中的具体边界是结合本项目现状作出的设计治理建议，不声称存在一个名为“双轨原型”的行业标准。

## 1. 结论先行

建议不要把现有大原型复制成两个“详略不同”的版本，而是建立两个回答不同问题的产品：

1. **客户体验原型（Customer Experience Prototype，CEP）**回答：“目标客户是否迅速理解、相信并想继续使用这个产品？”它是一个受控的体验假设，追求价值聚焦、流程连贯和品牌记忆点。
2. **实施对照原型（Implementation Reference Prototype，IRP）**回答：“团队是否对这个版本要实现的行为、状态、权限、数据和验收规则有共同理解？”它是 User Story 的可视化索引与行为参考，不是需求本身，也不是生产代码。

两者的共同内核应是**领域语言、角色责任、核心价值、政策承诺和经过批准的产品决议**；两者不能共用同一套运行时、数据源、发布入口和验收标准。客户原型给工程原型的交付物不是代码或全套页面，而是**验证过的证据、保留／否决的设计决策和待验证问题**。

这里最关键的理论依据是“按未知问题选择原型”而非“统一追求高保真”：NN/g 把界面原型定义为待检验的设计假设，并指出保真度至少分别存在于交互、视觉、内容／命令三个维度；原型类型应由测试目标决定，而不是由工具决定（[NN/g：UX Prototypes: Low Fidelity vs. High Fidelity](https://www.nngroup.com/articles/ux-prototype-hi-lo-fidelity/)）。因此，CEP 可以是**视觉与内容高保真、路径覆盖低保真**；IRP 可以是**状态与行为高保真、品牌视觉中保真**。

## 2. 术语建议

### 2.1 推荐名称

| 中文名称 | 英文缩写 | 一句话定义 | 刻意避免的误解 |
|---|---|---|---|
| 客户体验原型 | CEP | 用少量完整场景检验价值理解、信任与关键流程的体验假设 | 不是销售演示稿，不是完整 App，不是实施合同 |
| 实施对照原型 | IRP | 以 Story ID、场景、状态、权限和验收规则组织的交互式实施参考 | 不是“像素稿”，不是数据库／接口设计，不是生产代码 |
| 技术探针 | Spike | 为单一技术未知量做的限时实验，例如 OCR 成功率、微信跳转限制、Agent 延迟 | 不应塞进 CEP，也不应让 IRP 替代技术验证 |

不建议把第二类笼统命名为“系统原型”。“系统原型”容易同时被理解成架构验证、可运行 MVP 或准生产系统，使工程师误判其代码质量和权威性。IRP 更准确地表达了它是**用于对照的行为参考**。如果团队仍保留“工程原型”口语，应在仓库首页写明“工程原型 = IRP，不是技术架构原型”。

### 2.2 两类原型不是阶段关系

CEP 不必“完成后作废”，IRP 也不是 CEP 的加功能版。它们是两条长期并行、相互校验的学习回路：

- CEP 面向**产品方向与体验质量**，主要降低 desirability 风险。
- IRP 面向**共同理解与交付正确性**，主要降低需求歧义和遗漏风险。
- feasibility 风险应由技术探针、架构决议和真实集成测试承担；viability 风险还需要定价、运营和真实市场数据，不能由任一原型独自证明。

IDEO 将成功设计的约束区分为人的 desirability、技术 feasibility 和组织 viability（[IDEO：Introduction to Design Thinking](https://designthinking.ideo.com/introduction)）。Design Council 的 Double Diamond 又把理解／定义问题与开发／交付方案分开，并强调研究、学习、原型和测试会迭代往返（[Design Council：Double Diamond 历史与四阶段](https://www.designcouncil.org.uk/resources/the-double-diamond/history-of-the-double-diamond/)）。据此，把一个原型同时当作客户验证、工程规格、技术验证和交付证明，会混淆四类证据的效力。

## 3. 理论基础：为什么要拆

### 3.1 “想要什么”与“怎么做对”是不同研究问题

概念测试用对产品核心价值的近似表达，判断目标人群是否需要或想要它；可用性测试则让参与者在场景中完成任务，以改进具体设计。两者可以连续进行，但不能把“觉得概念不错”等同于“能顺利完成任务”（[NN/g：When to Use Which UX Research Methods](https://www.nngroup.com/articles/which-ux-research-methods/)）。CEP 应同时包含价值理解和少量行为观察，但其结论只能覆盖被测试的场景，不能外推为全系统可实现。

ISO 9241-210:2019 要求在人机交互系统的整个生命周期内开展以人为中心的设计活动（[ISO 9241-210:2019](https://www.iso.org/standard/77520.html)）；ISO 9241-11:2018 强调可用性是实际使用的结果，而非界面自身的装饰属性（[ISO 9241-11:2018](https://www.iso.org/standard/63500.html)）。因此，“让客户眼前一亮”应被转译为可观察的问题：他能否说出产品为谁解决什么问题、能否独立走完关键任务、是否理解数据与 Agent 的边界，而不是只评价页面是否漂亮。

### 3.2 User Story 是价值增量和持续对话，不是页面目录

Agile Alliance 明确指出：

- User Story 是对整体产品价值的一个功能增量；
- Story 是 Card、Conversation、Confirmation 所涵盖的共同知识，不是一份静态文档；
- Story 通常不对应某个技术组件或界面组件，按钮、弹窗和页面本身不是 Story；
- 产品方定义“做什么”，技术团队保留“怎么做”的创造空间（[Agile Alliance：User Stories](https://agilealliance.org/glossary/user-stories/)）。

所以 IRP 必须引用 User Story，但不能把“一个页面 = 一个 Story”或“原型所有可点击点 = 待开发需求”。原型只负责展示可观察行为；架构、组件拆分、接口策略、缓存和存储仍由工程设计决定。

### 3.3 Story Map 提供“全局旅程 + 可交付切片”

Jeff Patton 的 Story Mapping 方法先以“mile-wide, inch-deep”画出用户活动和高层任务作为 backbone，再向下补充子任务、替代路径、异常、后台行为和其他角色，最后横向切出完整的产品发布，而不是按页面或技术层切割（[Jeff Patton：Story Mapping 快速指南](https://jpattonassociates.com/wp-content/uploads/2015/03/story_mapping.pdf)）。这正适合 IRP：

- 左到右保持用户完成目标的时间顺序；
- 上到下放同一任务的细节、变化和异常；
- 每个 release slice 必须形成一个跨角色、可走通的端到端结果；
- 原型页面只是挂在 Story／场景下的视图，不是地图主干。

### 3.4 验收必须是可观察行为，而不是对着图“长得一样”

Acceptance Test Driven Development 要求客户／产品、开发和测试三种视角在实现前共同写出验收示例；这些示例既描述用户视角下系统如何工作，也用于验证实现（[Agile Alliance：ATDD](https://agilealliance.org/glossary/atdd/)）。Given–When–Then 将场景分为前置状态、行为和可观察后果（[Martin Fowler：GivenWhenThen](https://martinfowler.com/bliki/GivenWhenThen.html)）。

IRP 因而应围绕 `Given / When / Then` 场景组织，而不是要求生产 App 像素级复制。Agile Alliance 还警告，若验收测试过度依赖字段标签等界面细节，纯文案变化也会造成脆弱失败（[Agile Alliance：Acceptance Testing](https://agilealliance.org/glossary/acceptance-testing/)）。

### 3.5 原型代码默认不可进入生产

GOV.UK 的官方服务手册建议用原型在承诺建设前探索、分享、测试方案，但明确指出原型代码不需要达到生产安全、性能和流量标准，不应直接复制进生产；公开原型还应加访问保护，避免公众误认为真实服务（[GOV.UK Service Manual：Making prototypes](https://www.gov.uk/service-manual/design/making-prototypes)）。因此，CEP 与 IRP 即使都是 HTML，也必须带醒目的 prototype 标识、独立部署、假数据和无生产凭据；正式 App 只能依据批准的 Story／验收规则重新实现。

## 4. 两类原型的边界

| 维度 | 客户体验原型（CEP） | 实施对照原型（IRP） |
|---|---|---|
| 核心目标 | 验证目标客户能否理解价值、形成信任、顺畅完成 1–2 条关键任务，并记住最大差异点 | 让产品、开发、测试对某个 release slice 的行为、状态和边界形成可追踪的共同理解 |
| 主要受众 | 招募条件明确的真实潜在客户／早期用户；必要时包括合作方，但不能只给内部领导演示 | 产品负责人、交互／内容设计、客户端／前端、后端、AI、测试、安全与运营责任人 |
| 回答的问题 | “这是否值得用？”“为什么是近邻互助组？”“下一步在哪里？”“我信任它吗？” | “这个 Story 在什么前置条件下，由谁做什么，系统给出什么结果？”“异常与权限如何处理？” |
| 范围 | 只覆盖能表达核心价值的 golden path，以及会显著影响信任的一两个风险节点 | 覆盖本次发布切片内全部已承诺 Story；逐项包含主路径、变化、异常、跨角色交接和关键后台行为 |
| 信息架构 | 为首次理解优化，可隐藏暂不相关的复杂度；不必暴露完整设置和后台入口 | 展示 release slice 的完整导航／入口关系，并标出暂不实现、无权限和跨系统跳转 |
| 视觉保真度 | 高：品牌、内容层级、微信／小程序外壳、身份提示和关键动效接近目标体验 | 中到高：关键组件和文案语义准确；非关键视觉可用设计系统默认值，避免像素投入遮蔽行为问题 |
| 交互保真度 | 关键路径高，路径广度低；允许 Wizard of Oz 或预制 Agent 回答，但测试记录中必须披露模拟范围。Wizard of Oz 特别适合在 AI 未实现时验证交互假设（[NN/g：UX Prototypes](https://www.nngroup.com/articles/ux-prototype-hi-lo-fidelity/)） | 状态覆盖高；每个动作可定位到 Story／Scenario，必须能演示成功、失败、等待、返回与重试。AI 输出可夹具化，但要显式区分确定规则与概率行为 |
| 数据 | 合成的、易懂的代表性人物与内容；只为场景服务；不得使用真实联系方式、关系链、消费记录、会话或生产密钥 | 符合拟定 schema 的具名 fixture；覆盖边界值、空值、过期、权限差异、冲突和错误；不得直连生产库 |
| Agent | 重点验证身份是否看得懂、能力边界是否可信、回复节奏是否自然；预制回复不能被标成“真实 AI 能力” | 写明模型／规则／人工分别负责什么；覆盖超时、拒答、需真人确认、无知识、版本过期、越权请求和恢复路径 |
| 文档 | 一页测试说明：目标人群、2–3 个学习问题、任务脚本、模拟项、观察表和版本；IDEO 的原型计划模板同样要求先写学习问题、参与者与要收集的反馈（[IDEO.org：Prototyping Plan Template](https://www.designkit.org/methods/methods-pdf/Prototyping-Plan-Template.pdf)） | Story Map、Story／Scenario／Screen／State 追踪表、状态机、角色权限矩阵、数据字典、事件与接口草案、未决问题、版本和变更记录 |
| 验收方式 | 以真实目标参与者的行为证据验收：不解释时能否复述价值、独立完成任务、理解关键信任边界并选择合理下一步；偏好表态只作辅证，因为“人说的”和“人做的”常不同（[NN/g：UX Research Methods](https://www.nngroup.com/articles/which-ux-research-methods/)） | 以覆盖与无歧义验收：发布范围内 Story 100% 有场景；场景能找到前置、动作、可观察结果、权限和数据；产品／开发／测试完成共同走查；关键场景可转成验收测试 |
| 不能证明 | 真实留存／转化、规模化性能、安全合规、技术可行性、完整业务规则 | 市场真的想要、最终视觉一定受欢迎、架构能扩展、生产质量已达标 |
| 生命周期 | 每轮客户研究后可大改或丢弃；保留证据与决策，不必保留所有页面 | 随 release slice 版本化；实现后保留为历史参考，但生产行为与自动化验收成为最新事实 |

## 5. IRP 的最低覆盖清单

“工程师系统理解产品”不能靠增加页面数量实现，而要覆盖系统的可观察状态。每个进入当前 release slice 的 Story 至少检查：

1. **角色与权限**：谁发起、谁可见、谁可确认、Agent 代表谁、越权时发生什么。
2. **前置与入口**：从微信群、推荐卡、已有会话还是新需求进入；带入哪些已授权上下文。
3. **主路径**：最短成功路径及完成态。
4. **数据状态**：空、部分、过期、冲突、重复、被删除／撤回、不同证据等级。
5. **系统状态**：首次加载、处理中、成功、校验失败、网络失败、超时、重试、取消、幂等／重复提交。
6. **人工与 Agent 交接**：Agent 无法回答、需要服务者确认、真人晚到、承诺发生变更。
7. **跨边界行为**：跳转到服务者小程序、通知、授权摘要、返回后状态、接口失败。
8. **恢复与后果**：用户怎样知道发生了什么、能否撤销、谁收到通知、审计／履约事实如何变化。
9. **可访问性与设备约束**：键盘／焦点、可辨识标签、对比度、放大、读屏语义等应进入工程验收，不应因为客户原型未展示就被省略；Web 可参考 W3C 的现行 [WCAG 2.2 Recommendation](https://www.w3.org/TR/WCAG22/)。

Patton 的 Story Mapping 明确要求探索替代方式、异常、其他用户、业务规则和后台行为（[Story Mapping 快速指南](https://jpattonassociates.com/wp-content/uploads/2015/03/story_mapping.pdf)），所以“客户原型没画”不构成 IRP 省略异常状态的理由。

## 6. 共享什么，以及禁止共享什么

### 6.1 必须共享的语义内核

| 必须共享 | 原因 | 本项目例子 |
|---|---|---|
| 领域语言与禁用词 | 防止两个原型把产品说成两种东西 | 使用“亲历推荐”“近邻系统 Agent”“混合会话”，避免“获客卡”“平台担保” |
| 角色和责任 | 责任变化会直接改变产品与风险 | 服务者本人负责报价、接单与最终承诺；Agent 不伪装真人 |
| 核心价值与政策承诺 | 这是客户信任和工程规则的共同来源 | 数据属于用户、不售卖消费记录、推荐人无推荐收益 |
| 核心旅程 backbone | 保证客户故事与交付切片讲的是同一件事 | 外部求助 → 亲历回应 → 推荐卡 → 亲历详情 → 混合会话 |
| 已批准的内容语义 | 文案可能构成承诺，不能只当“视觉细节” | “本人陈述”与“双方确认记录”的区别 |
| 稳定标识与版本 | 才能追踪研究发现影响了哪个 Story | `US-CARD-01`、`SC-CARD-01-A`、CEP/IRP 版本号 |

### 6.2 可以共享，但必须版本化

- 设计 tokens、图标、头像和基础组件可以来自同一设计系统；CEP 可以更精致，IRP 仍须保持语义一致。
- 合成角色和示例内容可以共享，但 IRP 应扩充成状态 fixture，不能把 CEP 的一组故事数据误当成完整 schema。
- 核心路径的页面内容可以复制到 IRP，但复制后必须挂接 Story ID、状态和权限；后续变化由明确的源文件同步，不靠人工记忆。

### 6.3 禁止直接共享或继承

1. **禁止共享运行时和数据环境**：两个原型不得共用生产凭据、生产数据库、真实微信用户数据、真实关系链或可对外承诺的 Agent。
2. **禁止把 CEP 代码复制进生产**：即使 HTML 看起来完整，也不具备生产安全、性能、可维护性和测试保证；GOV.UK 对代码原型作了同样警告（[Making prototypes](https://www.gov.uk/service-manual/design/making-prototypes)）。
3. **禁止把 CEP 的可点击范围自动变成需求范围**：CEP 为了测试会故意隐藏分支、使用热点和预制回答。
4. **禁止把 IRP 当作客户研究材料直接外发**：调试入口、状态切换器、Story 标注和密集异常会污染客户对自然流程的判断。
5. **禁止以视觉相似替代行为验收**：生产 App 应通过 Story 验收场景，而不是只通过截图对比。
6. **禁止一个 URL 静默切换两种身份**：CEP 与 IRP 应有独立入口、标题和醒目的用途说明，避免工程师拿错版本，也避免客户把原型误认成真实服务。
7. **禁止未标注的“魔法”**：凡由主持人、假接口、固定延迟、预制 Agent、跳过权限或手工改状态实现的行为，都必须写入模拟清单。

## 7. 从 CEP 到 IRP 的交接机制

### 7.1 权威层级

发生冲突时，建议使用以下顺序，而不是默认“原型看起来怎样就怎样”：

1. 法律、安全、隐私与已公开政策；
2. 当前批准的产品决议和领域词典；
3. 当前 release slice 的 User Story、业务规则与验收场景；
4. IRP 的交互表现；
5. CEP 的交互表现；
6. 口头说明。

若 3 与 4 冲突，IRP 是缺陷；若 CEP 研究证明 2 或 3 有问题，应回到产品决策流程修改上游，再同步两份原型，不能让 CEP 静默成为新规格。

### 7.2 八步交接

1. **给 CEP 写学习合同**：每轮只列 2–3 个问题、目标参与者、任务和不能证明的事项。
2. **观察而非讲解**：让目标用户在外部求助的上下文中行动，记录行为、原话、失败点与主持人介入。NN/g 建议原型测试以安静观察为主，而非靠主持人与参与者聊天解释设计（[UX Prototypes](https://www.nngroup.com/articles/ux-prototype-hi-lo-fidelity/)）。
3. **产出决策日志**：每条发现标成 `保留 / 修改 / 否决 / 尚不确定`，附证据和影响范围；研究录屏不是工程规格。
4. **更新 Story Map**：把保留的价值路径放到 backbone；把变化、异常和其他角色补到纵向细节；决定进入哪个 release slice。Patton 要求 release slice 是跨越用户与完整使用过程的整体切片（[Story Mapping](https://jpattonassociates.com/wp-content/uploads/2015/03/story_mapping.pdf)）。
5. **举行 Story Workshop / Three Amigos**：产品、开发、测试共同讨论每个 Story，用具体示例暴露规则与问题；ATDD 的核心是这场跨视角对话，不是某个测试工具（[Agile Alliance：ATDD](https://agilealliance.org/glossary/atdd/)）。
6. **建立追踪表**：至少维护 `Decision → Story → Scenario → IRP screen/state → API/event → acceptance test`；尚未确定的项目必须显示为 question，不能由工程师猜。
7. **生成／更新 IRP**：先做发布切片的 happy path walking skeleton，再补当前切片的异常、权限、数据和恢复状态；每个页面可反查 Story／Scenario。
8. **实现前走查，开发中回放**：产品、开发、测试共同走完所有场景；开发中若技术约束改变行为，先更新决策／Story／场景，再更新 IRP。最终“完成”由生产代码的 Definition of Done 和验收测试证明，不由 IRP 证明。

### 7.3 推荐追踪表

| 字段 | 例子 |
|---|---|
| Decision ID | `DEC-2026-07-AGENT-ID` |
| 来源证据 | CEP v0.3，第 4/5 位用户误认两个 Agent 为同一方 |
| Story ID | `US-CHAT-02` |
| Story | 作为顾客，我要一眼区分真人、服务者 Agent 和近邻系统 Agent，以便知道谁能作出承诺 |
| Scenario ID | `SC-CHAT-02-B` |
| Given / When / Then | Given 服务者真人未加入；When Agent 回复价格问题；Then 标明 Agent 身份并要求真人确认 |
| IRP 状态 | `chat/provider-agent/needs-human-confirmation` |
| 数据／事件 | `actorType`, `commitmentAuthority`, `humanConfirmationRequested` |
| 验收层级 | 可自动化行为验收 + 人工可用性检查 |
| 未决问题 | 真人多久不响应后提示替代方案？ |

## 8. 反模式

1. **“一个大原型服务所有人”**：客户被异常矩阵淹没，工程师又从流畅演示中误读出不存在的规则。
2. **“CEP 是销售视频”**：主持人一路解释、只问“喜欢吗”，没有让客户实际行动。概念测试和可用性测试的问题不同，偏好表态不能替代行为证据（[NN/g：UX Research Methods](https://www.nngroup.com/articles/which-ux-research-methods/)）。
3. **“高保真 = 完整”**：画面精美却只有一个预设路径。NN/g 明确保真度在视觉、交互、内容上可以分别高低（[UX Prototypes](https://www.nngroup.com/articles/ux-prototype-hi-lo-fidelity/)）。
4. **“原型驱动 Story”**：逐屏拆 Story，导致“做一个弹窗”“接一个按钮”成为 backlog，丢失用户目标与价值。
5. **“IRP 等于前端规格”**：只描述界面，不描述后台状态、跨角色权限、通知、审计和失败恢复。
6. **“把假 AI 当能力承诺”**：CEP 中预制的完美回答没有标注，客户反馈和工程估算都建立在虚假能力上。
7. **“工程原型无限大全”**：把以后可能做的功能全部画全，不能切出可交付版本。Story Mapping 应先看全局，再切出整体而最小的 release（[Jeff Patton：Story Mapping](https://jpattonassociates.com/wp-content/uploads/2015/03/story_mapping.pdf)）。
8. **“原型代码顺手上线”**：原型环境通常没有生产级安全、性能与运维属性（[GOV.UK：Making prototypes](https://www.gov.uk/service-manual/design/making-prototypes)）。
9. **“截图就是验收”**：把标签、颜色、坐标写成脆弱验收，而没有验证用户行为和业务后果；Acceptance Testing 应表达产品行为和使用场景（[Agile Alliance：Acceptance Testing](https://agilealliance.org/glossary/acceptance-testing/)）。
10. **“双份原型双份真相”**：没有领域词典、Decision ID 和 Story ID，修改只发生在其中一份。

| 现在要回答的问题／变化 | 放在哪里 | 同步规则 |
|---|---|---|
| 客户能否在 30 秒内说出“消费者共享亲历、减少踩坑” | CEP | 研究结论进入 Decision Log；若定位改变，再更新共同语义内核 |

| 外部微信群到小程序卡片的核心跳转 | 两者 | CEP 验证连贯与价值；IRP 覆盖授权、失败、返回、卡片失效和不同角色 |
| 微信接口是否允许目标跳转与数据携带 | 技术探针 | 结论进入架构／接口决议；不要由 CEP 假跳转证明 |
| OCR 或 Agent 回答“看起来聪明” | CEP | 必须标注模拟；只能验证体验期待，不能证明模型质量 |
| OCR 低置信度、超时、识别错、用户纠正 | IRP + 技术探针 | IRP 定义用户可观察状态；Spike 给出真实能力和阈值证据 |
| 真人、服务者 Agent、近邻系统 Agent 的责任区分 | 共同非谈判内核 | CEP 检验是否看懂；IRP 覆盖每种身份、权限和交接场景 |
| 一张推荐卡展示哪些重点最吸引人 | CEP | 选定内容层级后同步 IRP；IRP 另补无头像、过期、未确认、撤回 |
| “本人陈述”和“双向确认记录”如何存储 | IRP + 数据／架构设计 | CEP 只验证表达是否理解；schema 与审计不由 CEP 决定 |
| 月卡价格在不同用户阶段如何计算 | IRP | CEP 只展示对客户最容易理解的代表情形；IRP 覆盖边界、变更和失败 |
| 页面颜色、插图、转场是否令人眼前一亮 | CEP | 通过品牌／可用性研究决定；只把选定 tokens 和组件状态同步 IRP |
| 加载、空、错误、重试、重复提交、权限拒绝 | IRP | 只在严重影响信任时抽一两个回 CEP 验证表达 |
| API、缓存、数据库、队列、模型供应商怎么选 | 架构决议／技术探针 | 不属于任一界面原型的权威范围 |
| 是否已达到可上线质量 | 生产 DoD、自动化测试、安全／性能／可访问性验证 | CEP 和 IRP 都不能单独批准上线 |

## 10. 对牛马互助平台的落地建议

### 10.1 CEP 应保留的最小故事

建议客户原型只讲清一条“外部求助被一段真实亲历接住”的完整故事：

1. 微信群里出现真实求助；
2. 亲历先行者用已有亲历或补录生成推荐卡；
3. 求助者点开后迅速明白“谁亲自用过、哪些事实匹配、证据是什么”；
4. 清楚看到数据承诺、无推荐收益和非平台担保；
5. 进入混合会话，并分辨服务者 Agent、近邻系统 Agent 与真人；
6. 自然走到一个下一步，例如了解服务、请求真人确认或提出新需求。

“眼前一亮”应集中在三个可复述记忆点：**亲历来自具体的人、Agent 不偷换责任、数据不拿去卖**。大量未来功能、预算明细、所有异常和全部后台状态不应抢占这条首次体验。

### 10.2 IRP 应按 Story Map 拆，而不是按四个手机壳拆

现有《近邻互助组 MVP 原型设计决议》的四个外层界面可以继续作为体验分镜，但 IRP 的主导航更适合按下列 backbone 组织：

`发现外部求助 → 理解需求 → 匹配／补录亲历 → 确认并分享 → 查看亲历 → 授权下一步 → 建立混合会话 → 真人确认／恢复 → 新需求`

每个任务下再按角色、状态和异常展开。这样工程师看见的是一个跨微信、推荐人、求助者、服务者和两个 Agent 的系统，而不是若干孤立屏幕。

### 10.3 建议的仓库隔离

```text
3-neighborhood-mutual-aid-team/
├── README.md                 # 文档地图与权威层级
├── index.html                # 两种原型的统一入口
├── prototype-customer/       # CEP：体验原型与测试说明
├── prototype-implementation/ # IRP：实施对照原型
├── product-decisions/        # 共同产品决议与研究依据
└── user-stories/             # Story、场景与验收规则
```

上述结构已在 2026-07-31 执行。两个原型在页面标题、README、URL 和视觉水印上分别显示用途。

## 11. 采用这套边界后的检查门

### CEP 可以进入客户测试

- 有明确目标人群和 2–3 个学习问题；
- 只展示要验证的完整关键故事；
- 所有假接口、假数据、预制 Agent 和主持人动作已列出；
- 不含真实个人数据和生产凭据；
- 已做内部 pilot，避免原型错误污染参与者心智；
- 研究脚本要求先观察行为，再追问态度。

### IRP 可以进入开发

- 当前 release slice 已确认，且每个 Story 能说明用户价值；
- Story Map 覆盖主干、其他角色、变化与异常；
- 每个 Story 至少有一组 Given–When–Then 验收场景；
- Story、Scenario、screen/state、数据／事件和验收测试可以互相追踪；
- 角色权限、Agent／真人责任、数据授权和跨系统边界已写明；
- 未决问题有负责人，不以“看原型自行理解”代替决策；
- 团队明确原型代码不进入生产。

### 产品可以宣称“已完成”

不能因为 CEP 测试顺畅或 IRP 覆盖完整就宣称完成。完成至少还需要：生产实现、通过验收测试、满足安全／隐私／性能／可访问性要求、可运维，并用真实使用数据继续验证价值。原型的职责是**便宜地暴露错误和建立共同理解**，不是替产品承担上线后的证据责任。
