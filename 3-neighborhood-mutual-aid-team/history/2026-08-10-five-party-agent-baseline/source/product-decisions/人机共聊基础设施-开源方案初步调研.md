# 《牛马互助平台》人机共聊基础设施：开源方案初步调研

- 检索日期：2026-08-10
- 研究范围：可自托管的人类—Agent 协作软件，以及“泛社交在平台外、用户与自己的 Agent 在服务号、服务者/消费者及双方 Agent 在小程序事项房间、Agent 后台协作在平台内”的跨渠道路线
- 资料口径：只采用项目官方文档、官方 GitHub 仓库、协议规范和许可证原文
- 文档性质：技术选型初筛，不是已经生效的架构决议；许可证判断也不构成法律意见

## 一、结论先行

进一步澄清后，产品不是泛社交聊天网络，但小程序仍需要围绕具体亲历或服务事项的受限群聊。整体包含四个通信面：

1. **无具体事项的人↔人：平台外。** 普通用户之间的泛社交继续在微信或其他既有社交平台；平台让亲历卡、授权摘要和房间入口能够跨平台携带。
2. **用户↔自己的 Agent：服务号为私有主入口。** 适合持续问答、任务进度和受微信规则限制的主动触达；用户授权后，个人 Agent 也可以加入小程序房间。
3. **消费者 + 消费者 Agent + 服务者 + 服务者 Agent + 近邻系统 Agent：小程序事项房间。** 这类似“商家本人与客服机器人共同服务消费者”，但消费者一侧也有自己的 Agent 自动提问、整理和协商；系统 Agent 同房管理事项边界、协作秩序与确认节点。
4. **服务者 Agent↔消费者 Agent：房间内或平台后台。** 可交换获授权的消息、结构化任务、证据、状态和确认请求；对用户判断有影响的消息应可追溯地投影回房间。

因此，平台仍需要真正的房间、成员、实时消息、历史和通知能力，但房间是一种有强业务边界的“服务事项”，而非通用社交群。首要基础设施变成**服务事项房间 + 跨渠道会话核心 + 双边 Agent 身份/授权 + 可审计事件帐本**。Zulip、Buzz、Matrix 可以作为房间后端或参考实现，但用户前台仍需要符合小程序和本领域责任边界的专用 UI。

核心不是一个“带聊天框的 Agent 产品”，而是五层可替换的基础设施：

1. **渠道适配层**负责服务号、小程序和外部分享卡的收发、身份换绑、重试与平台规则适配；渠道不拥有业务会话。
2. **服务事项房间层**负责成员、实时消息、历史、已读、通知、消息主体类型和房间生命周期；一个房间只属于一个具体事项。
3. **跨渠道会话核心**负责把同一事项中的服务号私有对话、小程序房间和 Agent 后台任务用稳定 ID 关联，并保存授权范围、责任主体、状态和审计事件。
4. **Agent 运行与编排层**负责模型调用、状态、工作流、人工审批、工具调用和失败恢复；它不应成为用户、授权或会话事件的唯一权威来源。
5. **工具与 Agent 协议层**负责解耦：Agent 通过 MCP 使用平台工具；Agent 间任务先采用平台内部结构化事件，确有跨运行时/跨组织互操作需求时再引入 A2A。

初步推荐是：

- **首选验证组合：已认证服务号 + 小程序服务事项房间 + 跨渠道会话核心/Gateway + LangGraph + MCP。** 服务号承载用户与自己 Agent 的私有对话；小程序房间承载消费者、消费者 Agent、服务者、服务者 Agent 和近邻系统 Agent 的同屏对话。微信的客服消息能力适合低门槛的一对一入口，但主动触达仍受窗口、额度、模板/订阅和运营规则约束，不能当成无条件推送通道。参见[接收普通消息](https://developers.weixin.qq.com/doc/service/guide/product/message/Receiving_standard_messages.html)、[客服消息规则](https://developers.weixin.qq.com/doc/service/guide/product/kf/intro.html)和[一次性订阅消息](https://developers.weixin.qq.com/doc/service/guide/product/message/One-time_subscription_info.html)。
- **Agent 间通信先自建最小结构化事件层，不急于选择人类聊天软件。** 第一版只需任务创建、接受/拒绝、证据引用、进度、完成/失败、请求真人确认和撤销；每个事件都带事项 ID、发送/接收 Agent、所属用户、授权来源和幂等键。
- **Buzz 是房间后端与内部运营台的高价值 PoC。** [Block Buzz](https://github.com/block/buzz) 把人、Agent、工作流和聊天建在同一套签名事件中继上，与“五方都拥有独立房间身份”的方向高度契合；但其客户端偏开发工作空间，移动端、推送、限流和审批仍有缺口。可以验证 Buzz Relay 是否能作为事项房间后端，但小程序前端与业务授权仍需自建。参见 [Buzz README](https://github.com/block/buzz/blob/main/README.md) 和[已验证的实现缺口](https://github.com/block/buzz/blob/main/ARCHITECTURE.md#9-known-limitations)。
- **若“开放协议、跨客户端、未来联邦”是核心战略：Matrix + Element + Agent Gateway + LangGraph + MCP。** Matrix 的房间与事件模型、客户端—服务器 API、应用服务 API都适合把 Agent 做成一等参与者，但组件多、端到端加密和联邦会显著增加工程与运维复杂度。参见 [Matrix 规范](https://spec.matrix.org/latest/)、[Application Service API](https://spec.matrix.org/latest/application-service-api/)和 [Element Web 仓库及许可证](https://github.com/element-hq/element-web)。
- **不建议用 Dify、Open WebUI 或 AutoGen 直接充当多人聊天底座。** 它们分别偏向低代码 Agent 应用平台、以 AI 为中心的 Web 前端、Agent 编排框架；都不能替代成熟聊天系统的房间、成员、权限和通知能力。Dify 与 Open WebUI 还有多租户/品牌限制；AutoGen 官方已经进入维护模式，新项目被建议迁往其后继框架。参见 [Dify 许可证](https://github.com/langgenius/dify/blob/main/LICENSE)、[Open WebUI 许可证](https://github.com/open-webui/open-webui/blob/main/LICENSE)和 [AutoGen 官方仓库说明](https://github.com/microsoft/autogen)。

## 二、我们实际要选的五层基础设施

| 层次 | 应负责 | 不应混入的责任 | 主要候选 |
| --- | --- | --- | --- |
| 渠道适配 | 服务号、小程序、分享卡的收发、验签、排重、身份换绑和失败补偿 | 成为用户、会话或授权的权威数据源 | 微信 API + 自建 Channel Gateway |
| 服务事项房间 | 房间成员、人/Agent 主体类型、实时消息、历史、已读、通知和房间关闭 | 生成平台级好友关系，或读取参与者的其他房间 | 自建房间服务；Buzz/Matrix/Zulip 后端 PoC |
| 跨渠道会话核心 | 用户、Agent、事项、消息、授权、责任主体、状态与审计事件 | 依赖某个微信 OpenID 或某个聊天产品的 room ID 表达业务关系 | 自建轻量服务 + 事件帐本 |
| Agent 运行与编排 | 提示与模型、短期/长期状态、工具调用、人工审批、重试、观测 | 成为唯一的用户目录、授权帐本或会话历史 | LangGraph；Dify（受许可证约束） |
| 工具与 Agent 协议 | MCP 工具调用；Agent 之间交换任务、证据、进度和确认请求 | 替代用户授权、会话存储或前端 UI | MCP；平台内部事件；将来可能的 A2A |

**关键架构原则：** 同一个事项可以跨越服务号、小程序和 Agent 内部网络，但每一次传递都必须有明确的发送主体、接收主体、所属用户、授权来源和最小数据范围。服务号 OpenID、小程序 session 和内部 Agent ID 都只是渠道身份，必须映射到平台自有的业务身份与事项 ID。

## 三、服务事项房间与 Agent 协作候选比较

以下软件可以候选小程序服务事项房间的后端，也可以只作为 Agent 协作与人工运营台。选型关键不是它们自带的 Web/桌面 UI 是否能直接给消费者用，而是房间、成员、人/Agent 身份、实时事件、权限和审计能否支撑我们自建小程序前端与事项边界。

### 3.2 重点候选解读

#### Zulip：最适合快速验证交互模型

Zulip 官方把 Bot 定义为一种“有受限权限的特殊用户”；Generic Bot 像普通用户一样通过 API 工作，Outgoing Webhook Bot 在收到私信或被提及时向指定 URL 发送 HTTP POST。Bot 可像人一样订阅频道、加入私密频道并受频道权限约束；官方明确建议使用满足需求的最小权限 Bot 类型。[机器人概览](https://zulip.com/help/bots-overview)

它的独特优势不是“功能最多”，而是 **频道 + 话题**：同一个互助组内，“找工作”“劳动争议”“本周拼车”等可以各自形成连续话题，Agent 不必在一个巨大时间线里猜上下文。实时事件 API 又允许 Gateway 只订阅指定频道/事件并立即响应。[实时事件 API](https://zulip.com/api/real-time-events)

风险是产品形态偏团队协作，面向普通社区用户时需要重新做中文引导、移动端体验验证和通知策略；它也没有原生 Agent 编排、工具审批和模型成本治理，这些仍要在 Gateway/编排层实现。

#### Matrix/Element：最强的开放性与长期扩展性

Matrix 把通信表示为房间中的事件，并把客户端同步、成员关系、权限事件、联邦和端到端加密写进开放规范。[Matrix 规范](https://spec.matrix.org/latest/) Application Service API 允许服务注册用户/房间别名命名空间，并代表大量虚拟用户工作，因此很适合让每个 Agent 拥有独立 Matrix 身份，而不是共享一个 Bot 账号。[Application Service API](https://spec.matrix.org/latest/application-service-api/)

代价是系统面更宽：至少要理解 homeserver、客户端、反向代理、媒体、数据库和密钥；一旦启用联邦/E2EE，消息可见性、密钥备份、历史补发、Bot 解密和事件重试都需要专门设计。Element Web 可自托管，但其许可证是 AGPL/GPL/商业多许可，不应简单标成“MIT”。[Element Web 仓库](https://github.com/element-hq/element-web) 因此更适合“开放通信网络是产品战略”，而不是仅为最快做出 MVP。

#### Block Buzz：不是单纯 Agent 框架，而是人与 Agent 共享的端到端工作空间

Buzz 的主体是一个可自托管工作空间：桌面端、人类或 Agent 客户端通过 WebSocket/REST 连接 `buzz-relay`，Relay 以 Nostr NIP-01 签名事件作为单一事实源，后面使用 Postgres、Redis 和 S3/MinIO。每个 Agent 有自己的密钥、通道成员关系和审计轨迹；`buzz-acp` 可把通道 `@mention` 事件排队后送给 1–32 个 ACP Agent 子进程，`buzz-cli` 和 MCP 工具则让 Agent 无需 GUI 即可操作平台。因此它横跨了本文的**聊天底座 + Agent Gateway/harness + 基础工作流**，不应与 LangGraph 这类纯编排库平行理解。参见 [README](https://github.com/block/buzz/blob/main/README.md)、[系统架构](https://github.com/block/buzz/blob/main/ARCHITECTURE.md)和 [Agent 架构](https://github.com/block/buzz/blob/main/VISION_AGENT.md)。

与本项目的贴合点是 Agent 原生身份、通道成员权限、完整审计、多社区隔离和 Apache-2.0 许可。但初步尽调也必须保留三个警示：

1. 它是 2026 年仍在快速建设的综合产品；官方“Works today”表明移动客户端仍在接线，推送通知仍属未实现设想。[README](https://github.com/block/buzz/blob/main/README.md)
2. 官方架构文档明确列出当前没有生产限流实现，工作流审批尚未端到端连通，`send_dm` 等部分工作流动作仍是 stub。[已验证的实现缺口](https://github.com/block/buzz/blob/main/ARCHITECTURE.md#9-known-limitations)
3. 官方单节点生产 Compose 仍依赖 Postgres、Redis、MinIO 和 Git 数据卷，并说明默认镜像跟踪 `main` 仅用于早期测试，需固定到 commit/semver。[生产 Compose 说明](https://github.com/block/buzz/blob/main/deploy/compose/README.md)

因此 Buzz 值得作为“我们是否还需自建 Gateway 与专用聊天 UI”的高信息量 PoC，但当前应按新兴工程底座而非成熟通用通信产品对待。

#### Mattermost 与 Rocket.Chat：成熟但更像企业协作套件

二者都有频道、线程、实时接口、Bot/Webhook、权限和自托管能力，做 Agent Gateway 并不困难。Mattermost 的集成入口包括 Webhooks、Slash Commands、Bot Accounts、REST/WebSocket 和 Plugin API。[Mattermost 集成文档](https://developers.mattermost.com/integrate/) Rocket.Chat 同时提供 REST、Realtime API 和 Apps-Engine。[Rocket.Chat 开发者文档](https://developer.rocket.chat/)

二者的主要选型成本是 **社区版/企业版边界和许可证尽调**，而不是基本聊天能力。Mattermost 的源码、官方编译版和管理工具存在不同许可口径；Rocket.Chat 的企业目录也有单独许可证。若团队已经有相应运维经验或需要企业协作能力，可进入 PoC；否则 Zulip 更简单，Matrix 更开放。

#### Discourse 与 Chatwoot：只适合相邻场景

- Discourse 很适合把高价值对话整理为可搜索、可审核的公共知识与长期讨论；其“主题—回复—信任等级”模型比实时群聊更适合社区治理。但把它当即时协作总线，会让通知和 Agent 响应显得笨重。
- Chatwoot 适合明确的服务请求：居民从网页/社交渠道发起会话，AI 先答，必要时转人工坐席。它的核心对象是 Inbox、Contact、Conversation 和 Agent，不是“普通成员共同在群里协作”，所以可作为未来的客服/转介入口，而非平台主聊天底座。

### 3.3 微信公众号：适合一对一 Agent 入口，不是多 Agent 聊天底座

微信公众号不是开源候选项，也不可自托管；它是一个可以放在 Agent Gateway 前面的专有接入渠道。腾讯官方对两类账号的定位是：订阅号偏信息传播，服务号向企业和组织提供更强的业务服务与用户管理能力。[腾讯官方产品说明](https://www.tencent.com/zh-cn/products/official-accounts/) 当前 API 兼容表显示，客服消息对“公众号”和“服务号”都要求企业主体已认证，而网页授权仅服务号可用；因此本项目应以**已认证服务号**作为 PoC 假设，不要以个人/未认证订阅号的权限做架构基线。参见[发送客服消息的适用范围](https://developers.weixin.qq.com/doc/service/api/customer/message/api_sendcustommessage)和[微信网页开发](https://developers.weixin.qq.com/doc/service/guide/h5/)。

| 维度 | 官方能力边界 | 对本项目的含义 |
| --- | --- | --- |
| 入站消息与超时 | 用户消息以 XML POST 到开发者 URL，`FromUserName` 是 OpenID；5 秒未响应会断开并最多重试 3 次。[接收普通消息](https://developers.weixin.qq.com/doc/service/guide/product/message/Receiving_standard_messages.html) | Webhook 必须验签、用 MsgId 排重、入队后立即回复 `success`；不应在 HTTP 请求里等 LLM |
| 回复与主动窗口 | 5 秒内可返回一个完整的被动回复；用户发消息后，客服消息当前为 48 小时内 5 条。点菜单/关注/扫码各是 1 分钟内 3 条。[被动回复](https://developers.weixin.qq.com/doc/service/guide/product/message/Passive_user_reply_message.html)、[客服消息规则](https://developers.weixin.qq.com/doc/service/guide/product/kf/intro.html) | 适合“用户问一次、Agent 回一次”；不适合多 Agent 互相发言、持续后台任务或高频通知 |
| Agent 路由 | 菜单 `click` 事件带自定义 key，`view` 可打开网页，`miniprogram` 可打开小程序；最多 3 个一级菜单、每个 5 个二级菜单。[创建自定义菜单](https://developers.weixin.qq.com/doc/service/api/custommenu/api_createcustommenu) | 可用 `OpenID + menu key/正文命令 + active_agent_id` 路由少量 Agent；Agent 可配置、并行任务或线程较多时应跳 H5/小程序 |
| 身份映射 | 同一用户对不同服务号的 OpenID 不同；绑定到同一微信开放平台后，可用 UnionID 统一多服务号、网站应用与小程序。[UnionID 机制](https://developers.weixin.qq.com/doc/service/guide/product/unionid.html) | OpenID 只是渠道身份；应映射到自有 `user_id`，再维护 `user_id ↔ agent_id`，不要把 OpenID 直接当全局账号 |
| 多 Agent 的 UI 身份 | 入站 schema 只有用户与公众号两个主体；客服 API 可指定 `kf_account`，并可管理客服头像/昵称。[客服消息介绍](https://developers.weixin.qq.com/doc/service/guide/product/kf/intro.html)、[发送客服消息](https://developers.weixin.qq.com/doc/service/api/customer/message/api_sendcustommessage) | **单公众号后端路由多 Agent 可行；多机器人作为独立参与者原生不支持。** 客服身份只是可验证的呈现近似，不是多 Bot 协议 |
| 流式与上下文 | 被动回复是完整 XML，客服消息是每次 POST 一个完整消息；另有 `Typing/CancelTyping` 状态，但要求前 30 秒有消息交互。[客服输入状态](https://developers.weixin.qq.com/doc/service/api/customer/message/api_typing) | **根据当前官方接口形态推断，没有通用 token 流式输出。** 不要用 5 条客服额度模拟 token 流；多轮记忆和 thread ID 全部在自建后端持久化 |
| 通知与合规 | 一次性订阅是“用户每授权一次，获得一次下发机会”；服务号群发对每个用户每月最多 4 条，不是个人会话补丁。[一次性订阅](https://developers.weixin.qq.com/doc/service/guide/product/message/One-time_subscription_info.html)、[群发规则](https://developers.weixin.qq.com/doc/service/guide/product/message/Batch_Sends.html) | 延迟任务完成通知需另做用户授权和模板/订阅设计；必须保留独立 Web/小程序入口与失败补偿 |
| AI 透明度 | 客服消息的 `aimsgcontext.is_ai_msg=1` 可在消息下方显示“内容由第三方AI生成”。[发送客服消息](https://developers.weixin.qq.com/doc/service/api/customer/message/api_sendcustommessage) | 建议默认开启该标记，并在自建帐本中记录实际 Agent/模型版本 |

推荐的公众号消息链路是：

```text
用户 ↔ 已认证服务号（同一个前台身份）
             ↓ Webhook：验签、MsgId 排重、入队、5 秒内 success
微信接入 Gateway（OpenID↔user_id、active_agent_id、限流、审计）
             ↓
LangGraph/Agent runtime（conversation_id、记忆、暂停/恢复） ↔ MCP 业务工具
             ↓
客服消息回送；复杂/流式/多任务 UI 跳 H5 或小程序
```

证据边界：本轮能直接读取微信当前服务号文档，上表引用的能力与额度均来自官方页面；“没有通用 token 流”和“不是多 Bot 协议”是从当前官方 schema/接口形态得出的架构推断。本轮没有用二手资料外推隐私、备案或生成式 AI 法律结论；这些需另做法务/合规专项。

## 四、Agent 运行与编排层比较

| 候选 | 定位与关键能力 | 许可证 | 自托管与运维 | 与共享聊天底座的关系 | 初步判断 |
| --- | --- | --- | --- | --- | --- |
| **LangGraph** | 用图和持久状态组织长运行 Agent；支持 checkpoint、暂停/恢复及人工审批。[Human-in-the-loop](https://langchain-ai.github.io/langgraph/concepts/human_in_the_loop/) | MIT，[许可证](https://github.com/langchain-ai/langgraph/blob/main/LICENSE) | 作为代码库嵌入服务；生产持久化、队列、观测仍需自行设计或采用商业平台 | 很适合放在 Gateway 后；一个聊天事件触发一个可恢复 run | **首选代码级编排内核** |
| **Dify** | 低代码构建 Chatbot、Agent、Workflow、RAG，并提供 API；支持社区版自托管。[官方仓库](https://github.com/langgenius/dify) | 修改版 Apache-2.0；未经书面授权不得运行源码多租户环境，前端改品牌也受限。[许可证](https://github.com/langgenius/dify/blob/main/LICENSE) | Docker 快速启动方便，但完整栈包含 API/Web、worker、PostgreSQL、Redis、向量库等，[自托管文档](https://docs.dify.ai/en/getting-started/install-self-hosted/docker-compose) | 可把每个 Dify App 包在 Gateway 后，通过 API 调用；不要让 Dify workspace 直接等同平台租户 | **可做低代码 PoC；多租户产品化前必须许可评估** |

### 为什么 LangGraph 比“低代码平台直接包办一切”更适合当前阶段

《牛马互助平台》的关键不是搭很多 Prompt，而是明确：哪个 Agent 看到了哪条消息、以什么权限调用工具、何时必须由人确认、超时/失败如何恢复、回复如何与原消息去重关联。LangGraph 的 checkpoint + interrupt/resume 能把这些做成显式状态机；官方文档说明暂停可持续数分钟、数小时乃至数日，因为执行上下文会写入 checkpoint，之后再恢复。[Human-in-the-loop 文档](https://langchain-ai.github.io/langgraph/concepts/human_in_the_loop/)

Dify 的优势是让非工程人员快速搭 Workflow/RAG，但它的 workspace 多租户限制与平台未来的组织模型可能冲突。稳妥做法是只把它当内部编排后端，经 Agent Gateway 调用其 API，并把用户、群组、消息、授权和审计留在平台侧。

## 五、集成协议：不要混为一谈

| 协议/接口 | 解决什么 | 不解决什么 | 本项目用法 |
| --- | --- | --- | --- |
| **聊天底座 Bot/API** | 收消息事件、判断房间/发送者、以 Agent 身份回消息；直接受房间权限约束 | Agent 内部状态机、跨业务工具标准化 | **现在必须有**；Gateway 的北向接口 |
| **MCP** | 用 JSON-RPC 客户端—服务器结构向 Agent 暴露 Tools、Resources、Prompts；支持 stdio 与 Streamable HTTP，[架构](https://modelcontextprotocol.io/docs/learn/architecture) | 不是人类群聊协议，也不定义房间、成员和消息历史 | **现在推荐**；把“查询互助资源、创建转介、读取规则”等封装为最小权限工具 |
| **A2A** | 让不透明的 Agent 应用通过 Agent Card、任务、消息、流式/推送机制互操作；Apache-2.0 Linux Foundation 项目，[官方仓库](https://github.com/a2aproject/A2A) | 不替代 MCP 的工具/上下文，也不替代聊天底座 | **暂缓**；当 Agent 来自多个独立运行时/组织且需要互派任务时再引入 |

MCP 官方明确说它只关注上下文交换，不规定 AI 应用怎样使用模型或管理上下文；Tools 是模型可调用动作，Resources 是上下文数据，Prompts 是模板。[MCP 架构](https://modelcontextprotocol.io/docs/learn/architecture) 它的规范也强调工具可能形成任意代码执行路径，应保留用户同意、访问控制和人工拒绝能力。[MCP 安全原则](https://modelcontextprotocol.io/specification/2025-03-26/index)

因此建议的跨渠道权限链是：

```text
服务号 / 小程序 / 内部 Agent 事件
  → Channel Gateway 验证渠道身份、排重、限流
    → 会话核心解析事项、发送/接收主体、授权和数据范围
      → 编排层判断当前状态与是否需要人工批准
        → MCP Server 再按用户 / Agent / 事项授权具体工具
          → 业务服务执行并写入同一事件帐本
```

任一层的“允许”都不能绕过下一层授权。Agent 能看到一段对话，不等于它能代表所属用户把这段内容传给另一个 Agent，更不等于它能对外作出承诺。

## 六、按新通信边界组合方案

### 方案 A：服务号 + 小程序事项房间 + 跨渠道会话核心 + LangGraph + MCP（推荐）

**适用：** 不做泛社交，但服务者与消费者需要围绕一个亲历/服务事项与双方 Agent 同房交互。

```text
泛社交：微信 / 其他社交平台
                 ↕ 亲历卡 / 房间入口
用户↔自己 Agent：服务号 ↔ Channel Gateway
                                      ↓
                跨渠道会话核心 / 事件帐本
                                      ↕
小程序服务事项房间：服务者 + 服务者 Agent
                         消费者 + 消费者 Agent
                         近邻系统 Agent
                                      ↕
                           LangGraph ↔ MCP 业务工具
```

优点是既不要求用户把既有社交关系搬入平台，又保留服务事项所需的双方真人、双方 Agent 与系统 Agent 同屏协作。缺点是我们必须承担小程序房间 UI、跨渠道一致性与更细的权限边界。

### 方案 B：方案 A + Block Buzz（事项房间后端 PoC）

**适用：** 希望直接复用 Agent-native 的房间、成员、签名消息和审计，并在其上自建小程序 UI 与业务权限。

优点是 Buzz 已经把真人和 Agent 做成同类的独立房间成员。缺点是它的现成客户端不适合消费者小程序，且业务事件可能与 Buzz 事件重复；需验证 Relay/API 能否作为可替换的房间后端。

### 方案 C：方案 A + Zulip（内部协作成熟度基线）

优点是 Bot、话题、通知和移动客户端更成熟，可快速验证运营人员怎样介入 Agent 任务。缺点是通用协作语义不是 Agent-native，需要 Gateway 把业务事件投影成消息。

### 方案 D：方案 A + Matrix（只在需要开放联邦时）

只有当 Agent 属于不同组织、需要开放协议互通、自有客户端或联邦时，Matrix 的复杂度才可能值得。它不应仅因“Agent 之间要聊天”就进入 MVP。

### 方案 E：Chatwoot + Agent runtime（仅客服/人工接管分支）

Chatwoot 仍适合“Agent 先答、平台人工客服接管”，但不应承载用户与他人 Agent 的主产品体验，也不应成为 Agent 间任务的权威数据源。

## 七、初步决策建议与 PoC 验收

### 推荐顺序

1. **先做方案 A 的端到端垂直切片。** 消费者在服务号让个人 Agent 发起事项，随后进入小程序房间；房间中服务者 Agent 先接待，双方 Agent 自动补齐信息，服务者与消费者都能看见过程并确认关键承诺。
2. **会话核心与房间模型同时优先。** 先定义 User、Agent、Matter、Room、Membership、Grant、Message/Task Event、Evidence Reference 和 Human Confirmation；任何微信或 Buzz/Zulip ID 都只是映射字段。
3. **用同一组验收测试自建房间与 Buzz 后端。** 比较五方成员身份、入房/离房历史、重复投递、真人确认、小程序实时性和运维成本；Zulip 可作为更成熟的通用房间对照组。
4. 只有开放联邦、自有客户端、E2EE、跨组织互通中至少两项是硬需求，才进入 Matrix PoC。
5. 新项目不选 AutoGen 为生产基线；Dify/Open WebUI 不能在许可证尽调前成为对外多租户 UI。

### PoC 必须验证的不是“能回复”，而是以下行为

- 消费者、消费者 Agent、服务者、服务者 Agent 和近邻系统 Agent 是否在同一房间中有独立、清晰、不可冒充的身份；系统 Agent 是否真正承担事项边界、协作秩序与确认节点管理。
- Agent 是否只能收到当前事项已授权的摘要和证据，而不是所属用户的其他服务号/小程序会话。
- 同一消息重复投递、服务重启和模型超时时，是否保证至多一次外部动作、可重试回复。
- 人工审批能否跨小时恢复；批准者身份、批准内容和最终工具参数是否可审计。
- 删除/编辑原消息、撤销授权、移出房间后，Agent 的缓存、checkpoint 和向量数据如何同步处理。
- 消息历史、Agent 内部状态、工具审计是否使用独立 ID 串联，而非只靠自然语言内容。
- 从服务号跳小程序、从小程序分享回微信人际对话时，是否只携带获授权的事项摘要，且 Matter ID 不断链。
- 公众号 Webhook 是否能稳定在 5 秒内 ack，并在重试、队列延迟和模型超时时不重复扣减 5 条客服额度。
- 用户能否明确知道当前 Agent；默认 Agent、菜单/H5 切换、`aimsgcontext.is_ai_msg` 标识与人工接管在真机上是否符合预期。
- 跨过 48 小时、客服额度用完、用户取消关注、access token 失效与微信 API 拒绝时，任务状态、通知与补偿路径是否可观测。

### 建议暂不做

- 不在第一版引入 Matrix 联邦、多个 Agent 框架、A2A 或泛社交聊天系统；服务事项房间本身不能删除。
- 不让 Agent 默认读取所属用户的全部会话，也不让它以真人身份代发消息。
- 不把聊天全文无期限复制进向量库；先确定保留期限、删除传播和敏感信息策略。
- 不让模型直接持有聊天管理员令牌或高权限业务 API key；由 Gateway/MCP Server 做凭证隔离和细粒度授权。

## 八、尚待确认的问题

1. 每个用户只有一个默认个人 Agent，还是可以拥有多个专家 Agent？用户与自己的多个 Agent 是否仍都经过同一服务号身份？
2. 服务者和消费者是自动成为房间成员，还是可以只派 Agent 入房？两位真人对 Agent 历史的可见性是否完全对称？
3. 双方 Agent 的后台自动协作是全量投影回房间，还是只投影结论、证据和需要真人决定的节点？
4. 服务号主动触达中，哪些消息是“任务结果”，哪些是运营内容？超过 48 小时后依赖什么用户授权和消息类目？
5. 项目主体是否已有或能完成服务号企业认证，以及客服消息、网页授权、小程序绑定的实际权限申请？
6. Agent 是用户自行创建，还是平台根据角色配置？Agent 能否创建转介、价格或支付类动作？
7. 中国大陆实际部署、微信平台运营、个人信息、生成式 AI 与数据跨境要求如何？本轮只做软件/API 能力初筛，不构成法务结论。
